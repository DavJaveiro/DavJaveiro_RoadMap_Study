A ideia de *soluções abstratas para problemas recorrentes* é a definição central do que chamamos de **Padrões de Projeto (Design Patterns)**. As fontes convergem ao tratar esse conceito não apenas como uma <span style="background:#affad1">ferramenta técnica</span>, mas como um meio de capturar conhecimento e facilitar a comunicação.

## A natureza da Abstração: Não é Código Pronto
As soluções não são código que podemos simplesmente copiar e colar ("copy-and-paste"). Olaf Musch enfatiza que um padrão descreve o objetivo e o que buscar, mas não uma implementação concreta, comparando-o a uma planta de construção que mostra onde as paredes estão, mas não como construí-las.

Martin Robillard reforça isso ao descrever a solução oferecida por um padrão como um "modelo de solução"  (*solution template*). Ele explica que a solução descreve os elementos do design, seus relacionamentos e responsabilidades, mas não descreve um design concreto específico, pois o padrão funciona como um molde. Wengner concorda, observando que os padrões de projeto "pairam acima" de um pedaço específico de código ou projeto.

No desenvolvimento de software, certas dificuldades aparecem repetidamente, independente do projeto. Não são erros de programação, mas desafios de *design* (projeto).

Olaf Musch explica que um padrão não é inventado, ele é descoberto. Se uma solução para um problema específico é usada com sucesso em três sistemas diferentes, ela é considerada um padrao.

**Exemplos de problemas:**
* *Como garantir que essa classe tenha apenas uma instância em todo o sistema?* (Problema #Singleton)
* *Como faço para que o objeto A avise o objeto B que algo mudou, sem que eles fiquem excessivamente dependentes um do outro?"* (Problema do Observer).
