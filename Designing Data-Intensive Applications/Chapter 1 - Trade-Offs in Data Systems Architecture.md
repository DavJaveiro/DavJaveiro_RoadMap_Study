## Preface
Existem centenas de bancos de dados para escolher. Qual devemos usar em nossa aplicação? A resposta curta é: "Depende". A resposta longa é... este livro.

Diferentes tecnologias para armazenar e processar dados fazem diferentes *trade-offs*, e nenhuma abordagem é a melhor para todas as situações. O sistema que é perfeito para uma aplicação pode ser totalmente inadequado para outra. Este livro é um guia por todo o panorama dos **data systems**, não apenas analisando um produto, mas comparando os pontos fortes e fracos de muitos sistemas.

Embora o cenário de tecnologias para processar e armazenar dados seja diverso e mude rapidamente, os princípios subjacentes permanecem. Se entendermos estes princípios, estaremos em posição de enxergar onde cada ferramenta se encaixa, como usá-la bem e como evitar suas armadilhas. Este livro foca nesses princípios.

Veremos neste livro, muitos exemplos de **data systems** bem-sucedidos: tecnologias que formam a base de inúmeras aplicações populares e que precisam atender a requisitos de escalabilidade, desempenho e confiabilidade em produção todos os dias. Vamos mergulhar no funcionamento interno desses sistemas, separar seus principais algoritmos e discutir os **trade-offs** que eles fizeram. Nesse jornada, tentaremos encontrar maneiras úteis de pensar sobre **data systems**, não apenas como eles funcionam, mas também por que funcionam dessa forma.

Depois de ler este livro, você estará em ótima posição para determinar quais tipos de tecnologias são apropriados para quais propósitos e para entender como ferramentas podem ser combinadas para formar a base de uma arquitetura de aplicação sólida. Você desenvolverá uma forte intuição sobre o que seus sistemas estão fazendo nos bastidores, para que possa raciocinar sobre seu comportamento, tomar boas decisões de design e rastrear quaisquer problemas que possam surgir.

## Trade-offs in Data Systems Architecture
*"Não existem soluções; existem apenas **trade-offs. [...]** Mas tentamos conseguir o melhor **trade-off** que pudermos, e é tudo o que podemos esperar.* - Thomas Sowell, entrevista com Fred Barnes (2005).

Os dados são centrais para grande parte do desenvolvimento de aplicações hoje em dia. Com aplicações web e mobile, **software as as service (SaaS)** e serviços em nuvem, tornou-se normal armazenar dados de muitos usuários diferentes em uma infraestrutura de dados compartilhada baseada em servidor. Dados provenientes de atividade de usuários, transações comerciais, dispositivos e sensores precisam ser armazenados e disponibilizados para análise. Conforme os usuários interagem com uma aplicação, eles tanto leem os dados que estão armazenados quanto geram mais dados.

Pequenas quantidades de dados, que podem ser armazenadas e processadas em uma única máquina, costuma ser relativamente fáceis de gerenciar. No entanto, à medida que o volume de dados ou a taxa de consultas cresce, eles precisam ser distribuídos por múltiplas máquinas, o que introduz muitos desafios. Conforme as necessidades da aplicação se tornam mais complexas, não é mais suficiente armazenar tudo em um único sistema podendo ser necessário combinar múltiplos sistemas de armazenamento ou processamento que ofereçam diferentes capacidades.

Chamamos uma aplicação de **data-intensive** se o gerenciamento de dados for um dos principais desafios no desenvolvimento da aplicação. Enquanto em sistemas **compute-intensive** o desafio é paralelizar uma computação muito grande, em aplicações **data-intensive** geralmente <span style="background:#fff88f">nos preocupamos</span> mais com coisas como <span style="background:#d3f8b6">armazenar</span> e <span style="background:#d3f8b6">processar grandes volumes de dados</span>, gerenciar mudanças nos dados, <span style="background:#d3f8b6">garantir consistência</span> diante de falhas e concorrência, e assegurar que os serviços <span style="background:#d3f8b6">estejam altamente disponíveis</span>.

Essas aplicações são tipicamente construídas a partir de blocos de construção padrão que fornecem funcionalidades comumente necessárias. Por exemplo, muitas aplicações precisam fazer o seguinte:
- Armazenar dados para que eles, ou outra aplicação, possam encontrá-los novamente mais tarde (**database**);
- Lembrar o resultado de uma operação cara, para acelerar leituras ( #caches);
- Permitir que usuários busquem dados por palavra-chave ou os filtrem de várias maneiras ( #search-indexes);
- Lidar com eventos e mudanças nos dados assim que eles ocorrem ( #stream-processing);
- Processar periodicamente um grande volume de dados acumulados ( #batch-processing)

Ao construir uma aplicação, normalmente pegamos vários sistemas ou serviços de software, como #databases ou #APIs, e os integramos com código de aplicação. Se estivermos realizando exatamente aquilo para o qual os #data-systems foram projetados, esse processo pode ser bastante fácil.

No entanto, à medida que a nossa aplicação se torna mais ambiciosa, surgem desafios. Existem muitos sistemas de banco de dados com características diferentes, adequados para diferentes propósitos, como escolher qual usar? Existem várias abordagens para cache, diversas maneiras de construir índices de pesquisa e assim por diante — como você raciocina sobre os prós e contras de cada um? Você precisa descobrir quais ferramentas e quais abordagens são as mais apropriadas para a tarefa em questão, e pode ser difícil combinar ferramentas quando você precisa fazer algo que uma única ferramenta não consegue fazer sozinha.

Nenhuma abordagem é fundamentalmente melhor que as outras; tudo tem prós e contras. Com este livro, aprenderemos a fazer perguntas certas para avaliar e comparar sistemas de dados, para que possamos descobrir qual a abordagem atenderá melhor às necessidades da nossa aplicação específica.

Começaremos a nossa jornada analisando algumas das maneiras como os dados são tipicamente usados nas organizações hoje. Muitas das ideias aqui têm origem em software corporativo (ou seja, as necessidades de software e práticas de engenharia de grandes organizações, como grandes corporações e governos), já que historicamente apenas as grandes organizações tinham os grandes volumes de dados que exigiam soluções técnicas sofisticadas. Se o seu volume de dados for pequeno o suficiente, você pode simplesmente mantê-lo em uma planilha! No entanto, mais recentemente também se tornou comum que empresas menores e startups gerenciem grandes volumes de dados e construam sistemas com uso intensivo de dados.

Um dos principais desafios com sistemas de dados é que pessoas diferentes precisam fazer coisas muito diferentes com os dados. Se trabalhamos em uma empresa, eu e a minha equipe teremos um conjunto de prioridades, enquanto outra equipe pode ter objetivos totalmente diferentes, mesmo que estejamos trabalhando com o mesmo conjuntos de dados! Além disso, esses objetivos podem não ser articulados explicitamente, o que pode levar a mal-entendidos e discordâncias sobre a abordagem correta.

**Terminologia: Frontends e Backends**
Muito do que discutiremos neste livro se relaciona ao desenvolvimento backend. Para explicar esse termo: em aplicações web, o código do lado do cliente (que roda em um navegador web) é chamado de frontend, e o código do lado do servidor que lida com as requisições do usuário é conhecido como backend. Aplicativos móveis são semelhantes aos frontends, pois fornecem interfaces de usuário que frequentemente se comunicam pela internet com um backend no servidor. Às vezes, os frontends gerenciam dados localmente no dispositivo do usuário [2], mas os maiores desafios da infraestrutura de dados geralmente residem no backend: um frontend precisa lidar apenas com os dados de um usuário, enquanto o backend gerencia dados em nome de todos os usuários. 

Um serviço backend geralmente é acessível via #HTTP (ou às vezes #WebSocket); ele costuma consistir em código de aplicação que lê e grava dados  em um ou mais bancos de dados e, por vezes, faz interface com sistemas de dados adicionais, como caches ou filas de mensagens (que podemos chamar coletivamente de infraestrutura de dados). O código da aplicação costuam ser sem estado (*stateless*, ou seja, quando termina de lidar com uma requisição HTTP, ele esquece tudo sobre aquela requisição), e qualquer informação que precise persistir de uma requisição para outra deve ser armazenada ou na infraestrutura de dados do lado do servidor.

**Insights Valiosos**
- **Arquitetura Stateless e Spring Security**: o texto reforça que o backend deve ser inerentemente *stateless*. Na prática com Java e Sprint Boot, isso exige o abandono da autenticação baseada em sessão em memória ( #HttpSession) no Spring Security. O padrão passa a ser o uso de JWT (JSON Web Tokens). O estado da autenticação reside no cliente (frontend), e o backend atua apenas validando a criptografia do token a cada requisição. Isso previne dores de cabeça severas em ambientes distribuídos, eliminando a necessidade de replicação de sessões entre diferentes nós do servidor.
- **A Jornada para Sistemas Distribuídos e Contêineres:** Migrar de um "nó único" para um "sistema distribuído" é onde a nuvem brilha. Uma aplicação Spring Boot _stateless_ é a candidata ideal para conteinerização com Docker. Uma vez em um contêiner, ferramentas de orquestração como Kubernetes (EKS na AWS) ou Amazon ECS podem escalar o serviço horizontalmente sem atrito. O backend esquece a requisição anterior, então não importa se a requisição "A" caiu no Pod 1 e a requisição "B" no Pod 2.
- **Sistemas Operacionais vs. Analíticos com Spring Data:** Um erro arquitetural clássico em aplicações Java é tentar executar relatórios complexos no mesmo banco de dados relacional que atende as transações dos usuários (OLTP via `Spring Data JPA` conectado ao Amazon RDS). À medida que a escala aumenta, é mandatório separar essas cargas, movendo os dados analíticos para data lakes ou <i>data warehouses</i> (como Amazon Redshift ou Athena) via rotinas de ingestão, para não comprometer a performance da aplicação em tempo real.
- **Integração com Infraestrutura de Dados AWS:** O texto cita a interface do backend com caches e filas de mensagens. No ecossistema Spring, essa integração é feita adotando o `Spring Data Redis` para acionar o Amazon ElastiCache (absorvendo picos de leitura e poupando o RDS) e o `Spring Cloud AWS` para enviar eventos ao Amazon SQS (desacoplando processos lentos e assíncronos da thread HTTP principal).
- **Boas Práticas de Documentação e Contratos API:** Como o backend gerencia dados "em nome de todos os usuários", a comunicação com o frontend deve ser perfeitamente orquestrada. A falta de estado significa que o payload HTTP deve conter todo o contexto necessário. Usar bibliotecas como `springdoc-openapi` para gerar documentação Swagger automaticamente garante que os desenvolvedores do frontend saibam exatamente qual o contrato de dados necessário, reduzindo falhas de integração e gargalos no CI/CD.

## Operational Versus Analytical Systems
If we are working on data systems in an enterprise, we are likely to encounter several different types of people who work with data. The first type are *backend engineers* who build services that handle requests for reading and updating data; this services often (frequentemente) serve external users, either directly or indirectly via other services (see "Microservices and Serverless" on page 21). Sometimes services are for internal use by other parts of the organization.

In addition to the teams managing backend services, two other groups of people typically require access to an organization's data: *business analysts*, who generate reports about the activities of the organization to help management make better decisions (*business intelligence, or BI*), and data *scientists* who look for novel insights in data or who create user-facing product features that are enabled by data analysis and machine learning (ML)/AI (e.g., "people who bought X also bought Y" recomendations on an ecommerce website, predictive analytics such as risk scoring or spam filtering, and ranking of search results).

Although business analysts and data scientists tend to use different tools and operate in different ways, <span style="background:#fff88f">they have some practices in common</span>. 
- First, both perform *analytics,* which means <span style="background:#fff88f">the look at the data that</span> the users and backend services have generated. 
- Second, they generally do not modify this data (except perhaps for fixing mistakes), although they might create derived datasets in which the original data has been processed in some way. 

This had led to a split between two types of systems, a distinction that we will use throughout this book:
- *Operational systems*: consist of the backend services and data infrastructure where the data is created, for example, by serving external users. Here, the application code both reads and modifies the data in its databases, based on the actions performed by the users.
- *Analytical systems:* serve the needs of business analysts and data scientists. The contain a read-only copy of the data from the operational systems, and they are optimized for the types of data processing that are needed for analytics. 

As we **shall** (**devemos**) see in the next section, #operational and #analytical systems are often kept separate, for good reasons (por bons motivos).  As these system have matured, two new specialized roles have emerged: *data engineers* and *analytics engineers*. *
- **Data Engineers** are the people who know how to integrate the operational and analytical systems and who take responsibility  for the organization's data infrastructure more widely (amplamente).  
- **Analytics engineers** model and transform data to make it more useful for the business analysts and data scientists in a organization.

Many engineers specialize in either the operational or the analytical side. However, this book covers both operational and analytical data systems, since both play an important role in the lifecycle of data within an organization. We will explore in depth the data infrastructure that is used to deliver services to both internal and external users so that we can work  better with our colleagues on the other side of this divide.

## Characterizing Transaction Processing and Analytics
In the early days of business data processing, a write to the database typically corresponded to a commercial transaction taking place: making a sale, placing an order with a supplier, paying an employee's salary, etc. As databases expanded into areas that didn't involve money changing hands, the term *transaction* nevertheless stuck, referring to a group of read and writes that form a logical unit. 

> Chapter 8 explores in detail what we mean by a transaction. This chapter uses the term loosely to refer to low-latency reads and writes.

Embora os bancos de dados tenham começado a ser usados para muitos tipos de dados, postagens de mídias sociais, jogadas em um jogo, contatos em um catálogo de endereços e muito, muito mais, o padrão básico de acesso permaneceu semelhante ao processamento de transações comerciais. Normalmente, um sistema operacional procura um pequeno número de registros por uma chave (isso é chamado de consulta pontual). Os registros são inseridos, atualizados ou excluídos com base na entrada do usuário. Como esses aplicativos são interativos, esse padrão de acesso ficou conhecido como <span style="background:#fff88f">processamento de transações on-line</span> ( #OLTP).

No entanto, os bancos de dados também começaram a ser cada vez mais usados para análise, que tem padrões de acesso muito diferentes em comparação com o OLTP. 

Normalmente, uma consulta analítica faz a varredura de um grande número de registros e calcula estatísticas agregadas (como contagem, soma ou média) em vez de retornar os registros individuais ao usuário. Por exemplo, um analista de negócios de uma rede de supermercados pode querer responder a consultas analíticas como estas:
- Qual foi a receita total de cada uma de nossas lojas em janeiro?
- Quantas bananas a mais do que o normal vendemos durante nossa última promoção?
- Qual marca de comida para bebês é mais frequentemente comprada junto com fraldas da marca X?

Os relatórios resultantes desses tipos de consultas são importantes para o BI, ajudando a gerência a decidir o que fazer em seguida. Para diferenciar esse padrão de uso de banco de dados do processamento de transações, ele foi chamado de processamento analítico on-line ( #OLAP). A diferença entre OLTP e analítica nem sempre é clara, mas algumas características típicas estão listadas na Tabela 1-1.

O significado de on-line em OLAP não é claro; provavelmente indica que as consultas não são apenas para relatórios predefinidos, mas que os analistas usam o sistema OLAP interativamente para consultar exploratórias.

Nos sistemas operacionais, os usuários geralmente não têm permissão para criar consultas SQL personalizadas e executá-las no banco de dados, pois isso poderia permitir que eles lessem ou modificassem dados que não têm permissão para acessar. Eles também podem escrever consultas cuja execução é cara e, portanto, afetar o desempenho do banco de dados para outros usuários. Por esses motivos, os sistemas OLTP executam, em sua maioria, conjuntos fixos de consultas incorporadas ao código do aplicativo, com consultas personalizadas únicas usadas apenas ocasionalmente para manutenção ou solução de problemas. Por outro lado, os bancos de dados analíticos geralmente dão aos seus usuários a liberdade de escrever consultas SQL arbitrárias manualmente ou de gerar consultas automaticamente usando uma ferramenta de visualização de dados ou de painel, como Tableau, Looker ou Microsoft Power BI.

Outro tipo de sistema é projetado para cargas de trabalho analíticas (consultas que agregam muito registros), mas incorporado a produtos voltados para o usuário. Os sistemas projetados para esse tipo de uso, conhecidos como análise de produtos ou análise em tempo real, incluem #Pinot, #Druid e #CLickHouse. Esses sistemas integerem dados em tempo real e são otimizados para responstas de consultas de baixa latência. Por outro lado, os sistemas OLAP tradicionais normalmente ingerem dados em lotes e são otimizados para o processamento de consultas de alto rendimento.

OLTP e OLAP não são tecnologias, são **padrões de acesso a dados.** A arquitetura que irá decidir separá-los, como separar e como sincronizar. Um único sistema não consegue ser ótimo para tudo, então nós otimizamos para escrita rápida OLTP ou para leitura analítica (OLAP), raramente os dois ao mesmo tempo. Portanto, OLTP e OLAP, são formas de uso dos dados. Não são bancos específicos, mas na prática, viram bancos diferentes. Separação evita gargalo e melhora escalabilidade.

## Data Warehousing
No início, os mesmos bancos de dados eram usados tanto para o processamento de transações quanto para consultas analíticas. O SQL se mostrou bastante flexível nesse aspecto; ele funciona bem para os dois tipos de consultas. No final da década de 1980 e início da década de 1990, no entanto, surgiu uma tendência de as empresas pararem de usar seus sistemas OLTP para fins de análise e, em vez disso, executarem a análise em um sistema de banco de dados separado. Esse banco de dados separado era chamado de *data warehouse*.

Uma grande empresa pode ter dezenas, até centenas, de sistemas OLTP: sistemas que alimentam o site voltado para o cliente, controlam sistemas de ponto de venda (checkout) em lojas físicas, rastreiam o estoque em armazéns, <span style="background:#fff88f">planejam rotas para veículos</span>, gerenciam fornecedores, administram funcionários e executam muitas outras tarefas. Cada um desses sistemas é complexo e precisa de uma equipe de pessoas para mantê-los, de modo que eles acabam operando de forma independente uns dos outros.

Geralmente, <span style="background:#fff88f">é indesejável que os analistas de negócios e cientistas de dados consultem diretamente esses sistemas OLTP</span>, por vários motivos:
- Os dados de interesse podem estar espalhados por vários sistemas operacionais, o que dificulta a combinação desses conjuntos de dados em uma única consulta (um problema conhecido como silos de dados) *data silos*.
- Os tipos de esquemas e layouts de dados que são bons para OLTP são menos adequados para análise (consulte Start and Snowflakes, esquemas para análise).
- As consultas analíticas podem ser bastante caras e executá-las em um banco de dados OLTP afetaria o desempenho de outros usuários;
- Os sistemas OLTP podem residir em uma rede separada à qual os usuários não tem permissão para acessar diretamente, por motivos de segurança ou conformidade.

Um *data warehouse*, por outro lado, é um banco de dados separados que os analistas podem consultar à vontade  , sem afetar as operações OLTP. Como veremos no capítulo 4, os data warehouse geralmente <span style="background:#fff88f">armazenam dados</span> de forma muito <span style="background:#d3f8b6">diferente dos bancos de dados OLTP,</span> para otimizar os tipos de consultas que são comuns na análise. 

O *data warehouse* contém uma cópia somente de leitura dos dados de todos os sistemas OLTP da empresa. Os <span style="background:#fff88f">dados são extraídos dos bancos de dados OLTP</span> (por meio de um despejo periódico de dados ou de um fluxo contínuo de atualizações), transformados em um esquema de fácil análise, limpos e, em seguida, carregados no data warehouse. Esse processo de obtenção de dados para o data warehouse é conhecido como <span style="background:#fff88f">extração-transformação-carregamento</span> (ETL) e está ilustrado na Figura 1.1. Às vezes, a ordem das etapas de transformação e carregamento é trocada (ou seja, a transformação é feita no data warehouse, depois do carregamento), resultando em ELT.

!![image-2026416223702.png](/image-2026416223702.png)

Em alguns casos, as <span style="background:#fff88f">fontes de dados dos processos de ETL</span> são produtos SaaS externos, como gerenciamento de relacionamento com o cliente (CRM), marketing por e-mail ou sistemas de processamento de cartão de crédito. Nesses casos, não temos acesso direto ao banco de dados original, pois ele é acessível somente por meio da API do fornecedor do software. Trazer os dados desses sistemas externos para o seu próprio data warehouse pode permitir análises que não são possíveis por meio da API de SaaS. A ETL para APIs de SaaS geralmente é implementada por serviços especializados de conector de dados, como Fivetran, Singer ou Airbyte.

Alguns sistemas de banco de dados oferecem processamento transacional/analítico híbrido (HTAP), que visa permitir OLTP e análise em um único sistema sem exigir ETL de um sistema para outro. No entanto, muitos sistemas HTAP consistem internamente em um sistema OLTP acoplado a um sistema analítico separado, oculto por trás de uma interface comum, portanto, a distinção entre os dois continua sendo importante para entender como esses sistemas funcionam.

Além disso, embora existe o HTAP, é comum haver uma separação entre os sistemas transacionais e analíticos devido a seus <span style="background:#fff88f">diferentes objetivos e requisitos</span>. Em particular, é considerada uma boa prática que cada sistema operacional tenha seu próprio banco de dados (consulte "Microsserviços e sem servidor"), o que pode resultar em centenas de banco de dados operacionais separados; por outro lado o HTAP, portanto, não substituiu os data warehouse. Em vez disso, ele é útil quando o mesmo aplicativo precisa realizar consultas analíticas que examinam um grande número de linhas e ler e atualizar registros individuais com baixa latência. A detecção de fraudes pode envolver essas cargas de trabalho, por exemplo.  

<span style="background:#fff88f">A separação entre sistemas operacionais e analíticos faz parte de uma tendência mais ampla.</span> À medida que as cargas de trabalho se tornaram mais exigentes, os sistemas se tornaram mais especializados e otimizados para determinadas cargas de trabalho. Os sistemas de uso geral podem lidar confortavelmente com pequenos volumes de dados, mas quanto maior a escala, mais especializados os sistemas tendem a se tornar.

### From data warehouse to data lake
Um *Data Warehouse* frequentemente utiliza um modelo de dados relacional que é consultado por meio de SQL, possivelmente utilizando software especializado de BI. Este modelo funciona bem para os tipos de consultas que os analistas de negócios *business analysts* precisam realizar, mas é menos adequado às necessidades dos *data scientists* ao realizarem tarefas como estas:
- **Transformar os dados:** em um formato adequado para treinar um modelo ML. Isso frequentemente exige converter as linhas e colunas de uma tabela de banco de dados em um vetor ou matriz de valores numéricos denominados *features*. O processo de realizar essa transformação visando maximizar o desempenho do modelo treinado é chamado *feature engineering*, e frequentemente requer código personalizado, que pode ser difícil de expressar utilizando apenas SQL.
- **Utilizar técnicas de Natural Language Processing (NLP):** em dados textuais (por exemplo, avaliações de um produto) para tentar extrair informações estruturadas delas (como o sentimento do autor ou os tópicos mencionados). Da mesma forma, os *data scientists* podem precisar extrair informações estruturadas de fotografias, utilizando técnicas de #Computer-Vision.

Embora tenha havido esforços para adicionar operadores de ML a um modelo de dados SQL e para construir sistemas de ML eficientes sobre uma base relacional, muitos *data scientists* preferem não trabalhar dentro de um banco de dados relacional, como uma *data warehouse*. Em vez disso, muitos optam por usar bibliotecas de análise de dados em Python, como Pandas e scikit-learn, linguagens de análise estatística como R e *frameworks* de análise distribuída como o Spark [14]. Discutiremos esses tópicos com mais detalhes em "DataFrames, Matrices, and Arrays¨ na página 105.

Consequentemente, as organizações precisam disponibilizar os dados em uma forma que seja adequada para o uso por *data scientists*. A solução é um *data laker*: um repositório centralizado de dados que armazena uma cópia de qualquer informação que possa ser útil para análise, obtida de sistemas operacionais por meio de processos ETL.

A diferença para uma *data warehouse* é que uma *data lake* simplesmente contém arquivos, sem impor nenhum formato de arquivo, modelo de dados ou esquema específico. Os arquivos em um *data lake* podem ser coleções de registro de banco de dados, codificados utilizando um formato de arquivo como Arvro ou Parquet, mas uma *data lake* pode igualmente conter texto, imagens, vídeos, leituras de sensores, *matrizes esparsas*, *features vectors*, sequências genômicas ou qualquer outro tipo de dados. Além de ser mais flexível, um *data lake* também costuma ser mais econômica do que o armazenamento de dados relacionais, já que pode utilizar armazenamento de arquivos *commoditized* (de padrão de mercado/econômico), como *object stores*.

Os processos ETL foram generalizados como *data pipelines* (ou dutos de dados) e, em alguns casos, a *data lake* tornou-se uma parada intermediária no caminho entre os sistemas operacionais e a *data warehouse*.  A *data lake* contém os dados na forma "raw" (bruta/crua) produzida pelos sistemas operacionais, sem sofrer a transformação para um esquema de *data warehouse*m relacional. Essa abordagem tem a vantagem de que cada consumidor dos dados pode transformar os dados brutos na forma que melhor atender às suas necessidades. Frequentemente, isso é chamado de princípio do sushi: "dados crus são melhores".

## Além da *data lake*
À medida que as práticas de *analytics* amadureceram, as organizações vêm prestando cada vez mais atenção à gestão e operação de sistemas analísticos e *data pipelines*, algo expresso, por exemplo, no *DataOps Manifesto*. Isso tem sido impulsionado parcialmente por questões de governança, privacidade e *compliance* com regulamentações como o *Gengeral Data Protection Regulation *(GDPR)* e a *California Consumer Privacy Act (CCPA).*

Os dados utilizados em análises estão sendo disponibilizados não apenas como arquivos e tabelas relacionais, mas também como * #streams* de eventos. Como a análise de dados baseada em arquivos (*file-based*), é possível reexecutar a análise periodicamente (por exemplo, diariamente) para acompanhar alterações nos dados; já o *stream processing* permitem que os sistemas analíticos respondam aos eventos muito mais rapidamente, na ordem de segundos. Dependendo da aplicação e da sua sensibilidade temporal, uma abordagem baseada em *stream processing* pode ser extremamente valiosa, por exemplo, para identificar e bloquear atividades potencialmente fraudulentas ou abusivas.

Em alguns casos, as saídas de sistemas analíticos são disponibilizadas para sistemas operacionais (um processo muitas vezes denominado *reverse ETL*). Por exemplo, um modelo ML, treinado com dados de um sistema analítico, pode ser implantado em *production* para gerar recomendações para usuários finais, como "pessoas" que compraram X também compraram Y". Modelos de aprendizado de máquina (*machine learning*) podem ser implantados em sistemas operacionais utilizando ferramentas especializadas como TFX, Kuberflow ou MLflow.

#stream-processing 
O stream processing transforma a maneira como sistemas consomem e entendem dados ao tratar fluxos contínuos como entidades processáveis. Sua relevância se sustenta em cinco pilares:
1.  **Baixa latência e decisões em tempo real**: ao contrário do batch processing (que opera em janelas fixas), o stream processa dados conforme chegam, permitindo respostas na ordem de milissegundos a segundos. Críticos para deteção de fraude, monitoramento industrial, recomendações dinâmicas e resposta a incidentes.
2. **Processamento stateful e contextual**: permite manter estado entre eventos ao longo do tempo, janelas temporais windowing, agregações contínuas, correlações e enriquecimento com referências externas, sem precisar reprocessar históricos completos. 
3. **Escalabilidade horizontal e resiliência nativas**: frameworks modernos dividem stream em partições, permitem reequilíbrio automático rebalacing e oferecem garantias de entrega (at-least-once, exactly-once), com checkpointing e recovery automático sem perda de dados.
4. **Arquitetura event-driven e cloud-native** alinha-se naturalmente a padrões modernos: microsserviços reativos, CDC (Change Data Capture), IoT, e ecossistemas que substituem filas tradicionais por brokers duráveis de eventos.
5. **Complementaridade com batch (Lambda / Kappa)**  
    O stream cuida da frescura operacional e alertas imediatos; o batch garante consistência histórica e modelos treinados offline. Muitas organizações hoje migram para arquiteturas Kappa, onde um único pipeline serve ambas as necessidades.

2. **"Existe uma sequência de ações dependendo de outras?**"
	1. Exemplo: receber evento A, depois B, e depois C..." -> Stream é bom.
	2. Exemplo: "Guardar esse arquivo e esquecer."-> banco relacional serve melhor.

## Systems of Record and Derived Data
Relacionada à distinção entre sistemas operacionais e analíticos, esta obra também diferencia **sistemas de registro** e **sistemas de dados derivados**. Esses termos são úteis porque ajudam a esclarecer o fluxo de dados por meio de um sistema:

**Sistemas de registro**
Um <span style="background:#fff88f">sistema de registro</span>, também conhecido como fonte da verdade (*source of truth*), <span style="background:#d3f8b6">contém a versão autoritativa ou canônica dos dados</span>. Quando novos dados são recebidos, por exemplo, como entrada do usuário, eles são gravados aqui primeiro. <span style="background:#b1ffff">Cada fato é representado exatamente uma vez</span> (a representação é tipicamente normalizada; consultar **"Normalização, Desnormalização e Junções"** na página 72). Se houver qualquer discrepância entre outro sistema e o sistema de registro, o valor no sistema de registro é (por definição) o correto. 

**Sistemas de dados derivados**
Os <span style="background:#fff88f">dados em um sistema derivado</span> são o resultado da obtenção de dados existentes de outro sistema e de sua transformação ou processamento de alguma forma. Se perdermos os dados derivados, podemos recriá-los a partir da fonte original. Um exemplo clássico é o *cache*: os dados podem ser servidos a partir do *cache* se estiverem presentes, mas, caso ele não contenha o que precisamos, é possível recorrermos ao banco de dados subjacente. Valores desnormalizados, índices, visões materializadas, representações de dados transformadas e modelos treinados em um conjunto de dados também se enquadram nessa categoria.

Tecnicamente falando, os dados derivados são redundantes, no sentido de que duplicam informações existentes. No entanto, esses dados costumam ser essenciais para obter um bom desempenho em consultas de leitura. <span style="background:#fff88f">É possível derivar vários conjuntos de dados a partir de uma única fonte</span>, o que <span style="background:#d3f8b6">permite analisar os dados sob diferentes perspectivas</span>.

Os sistemas analíticos geralmente são sistemas de dados derivados, pois são consumidores de dados criados em outro lugar. Os serviços operacionais podem conter uma mistura de sistemas de registros e sistemas de dados derivados. Os sistemas de registro são os bancos de dados primários nos quais os dados são gravados inicialmente, enquanto os sistemas de dados derivados são os índices e *caches* que aceleram as operações comuns de leitura, especialmente para consultas que o sistema de registro não consegue responder de forma eficiente.

A maioria dos bancos de dados, mecanismos de armazenamento e linguagens de consulta <span style="background:#fff88f">não são, por natureza, sistemas de registro ou sistemas derivados</span>. Um banco de dados é apenas uma ferramenta; a forma como utilizamo-os depende de nós. A distinção entre um sistema de registro e um sistema de dados derivados não depende da ferramenta, mas da maneira como a empregamos em nossa aplicação. Ao <span style="background:#fff88f">deixar claro quais dados são derivados de quais outros</span>, é possível trazer clareza a uma arquitetura de sistema que, de outra forma, seria confusa.

Quando os dados em um sistema são derivados dos dados em outro, precisamos de um processo para atualizar os dados derivados sempre que a informação original no sistema de registro for alterada. Infelizmente, muitos bancos de dados são projetados com base na suposição de que a nossa aplicação sempre precisará usar apenas aquele único banco de dados, e não facilitam a integração de múltiplos sistemas para propagar essas atualizaçoes. No capítulo 11, discutiremos os *pipelines* de dados como uma abordagem para a integração de dados, o que nos permite compor vários sistemas de dados par alcançar objetivos que um único sistema não conseguiria atingir sozinho.

Isso nos leva ao fim da nossa comparação entre análise de dados (analytics) e processamento de transações. Na próxima seção, examinaremos outro *trade-off* que provavelmente já debatemos diversas vezes.

Dados de registro são a fonte da verdade; derivados otimizam a leitura. A distinção está no uso, não na ferramenta. Clareza sobre derivações simplifica arquitetura, evita inconsistências e facilita integrações entre sistemas. 

## Cloud Versus Self-Hosting
Para qualquer atividade que uma organização precise realizar, uma das primeiras questões é se ela deve ser feita internamente ou terceirizada. Ou seja, devemos construir ou comprar? No fundo, essa é uma questão sobre prioridade de negócio. Uma regra prática comum é que atividades que representam uma competência central ou uma vantagem competitiva para a nossa organização devem ser feitas internamente, enquanto atividades não essenciais, rotineiras ou comuns devem ser deixadas para um fornecedor. Para dar um exemplo extremo: a maioria das empresas não fabrica seus próprios CPUs, pois é mais barato comprá-los de fabricantes de semicondutores.

No contexto de software, duas decisões importantes são: quem constrói o software e quem o implanta (deploy). O espectro de possibilidades é ilustrado na Figura 1-2. Em um extremo, está o software sob medida (*bespoke*), que desenvolvemos e operamos internamente; no outro extremo, estão os serviços em nuvem amplamente utilizados ou produtos SaaS, implementados e operados por um fornecedor externo, aos quais acessamos apenas por meio de uma interface web ou *API*.

O meio-termo é o software *off-the-shelf* (de prateleira - open source ou comercial) que nós mesmos hospedamos ou implantamos, por exemplo, ao baixar o MySQL e instalarmos em um servidor sob o nosso controle. Isso pode ser feito em nosso próprio hardware (frequentemente chamado de *on-premises*, mesmo que o servidor esteja em um rack de datacenter alugado e não literalmente em nossas instalações), ou em uma máquina virtual (VM) na nuvem (Infrastructure as a Service, ou IaaS). Há mais pontos ao longo desse espectro, como pegar um software open source e executar uma versão modificada dele.

Uma questão relacionada é como implantamos serviços, seja na nuvem ou *on-premises*, por exemplo, se utilizamos um *framework* de orquestração como o Kubernetes. No entanto, a escolha de ferramentas de implantação está além do escopo deste livro, pois outros fatores exercem influência maior sobre a arquitetura de sistemas de dados.

## Pros and Cons of Cloud Services
Utilizar um serviço em nuvem, em vez de executar um software comparável por conta própria, essencialmente terceiriza a operação desse software para o provedor de nuvem. Existem bons argumentos a favor e contra essa abordagem. Provedores de nuvem afirmam que usar seus serviços economiza tempo e dinheiro e permite que avancemos mais rapidamente em comparação com a configuração de nossa própria infraestrutura. 

No entanto, se o uso de um serviço em nuvem é realmente mais barato e fácil do que o *self-hosting* depende muito das nossas habilidades e da carga de trabalho dos nossos sistemas. Se temos experiência configurando e operando os sistemas de que precisamos e a nossa carga é bastante previsível (ou seja, o número de máquinas necessárias não flutua drasticamente), geralmente é mais barato comprar nossas próprias máquinas e executar o software nelas mesmo.

Por outro lado, se você precisa de um sistema que ainda não sabe como implantar e operar, adotar um serviço em nuvem costuma ser mais fácil e rápido do que aprender a gerenciar o sistema. Contratar e treinar pessoal especificamente para manter e operar o sistema pode sair muito caro. Você ainda precisa de uma equipe de operações ao usar a nuvem (consulte "Operações na Era da Nuvem" na página 17), mas terceirizar a administração básica do sistema pode liberar sua equipe para focar em preocupações de nível mais alto.

Terceirizar a operação de um sistema para uma empresa especializada em executá-lo pode resultar, potencialmente, <span style="background:#fff88f">em um serviço melhor</span>, já que o provedor ganha expertise operacional ao fornecer o serviço para muitos clientes. Por outro lado, se você mesmo executa o serviço, pode configurá-lo e ajustá-lo para ter um bom desempenho na sua carga de trabalho específica. É improvável que um serviço em nuvem esteja disposto a fazer tais personalizações em seu nome.

Serviços em nuvem são particularmente valiosos se a carga nos seus sistemas variar muito ao longo do tempo. Se você provisionar suas máquinas para lidar com a carga de pico, mas esses recursos computacionais ficarem ociosos a maior parte do tempo, o sistema se torna menos custo-efetivo. Nessa situação, os serviços em nuvem têm a vantagem de facilitar o dimensionamento (_scaling_) dos seus recursos computacionais para cima ou para baixo em resposta a mudanças na demanda.

Por exemplo, **sistemas analíticos** frequentemente apresentam a carga extremamente variável. Executar rapidamente uma consulta analítica grande requer muitos recursos computacionais em paralelo, mas, em vez de concluída a consulta, esses recursos ficam ociosos até que um usuário faça a próxima consulta. Consultas predefinidas (por exemplo, para relatórios diários) podem ser enfileiradas e agendadas para suavizar a carga, mas, para consultas interativas, quanto mais rápido quisermos que elas sejam concluídas, mais variável se torna a carga de trabalho. Se um conjunto de dados for tão grande que consultá-lo rapidamente exigir recursos computacionais significativos, usar a nuvem pode economizar dinheiro, pois podemos devolver recursos não utilizados ao provedor, em vez de deixá-los ociosos. Para conjuntos de dados menores, essa diferença é menos significativa. 

A maior desvantagem de um serviço em nuvem é que você não tem controle sobre ele:
- Se faltar um recurso que você precisa, tudo o que você pode fazer é pedir educadamente ao fornecedor que o adicione; geralmente, você não pode implementá-lo por conta própria.
- Se o serviço cair, tudo o que você pode fazer é aguardar a recuperação.
- - Se você estiver usando o serviço de uma forma que acione um _bug_ ou cause problemas de desempenho, diagnosticar o problema será difícil. Com um software que você mesmo executa, é possível obter métricas de desempenho e informações de _debug_ do sistema operacional para ajudar a entender seu comportamento, além de consultar os _logs_ do servidor. Com um serviço hospedado por um fornecedor, geralmente você não tem acesso a esses internos.
- Se o serviço for descontinuado, tornar-se inaceitavelmente caro ou se o fornecedor alterar o produto de uma forma que você não aprova, você fica à mercê dele; continuar executando uma versão antiga do software geralmente não é uma opção, então você será forçado a migrar para um serviço alternativo [23]. Esse risco é mitigado se serviços alternativos expuserem uma _API_ compatível, mas, para muitos serviços em nuvem, não há _APIs_ padronizadas, o que eleva o custo de troca, tornando o _vendor lock-in_ um problema.
- Se o provedor de nuvem estiver em outro país e surgir um conflito político entre esse país e o seu, você corre o risco de ser bloqueado do serviço devido a sanções impostas.
- É necessário confiar que o provedor de nuvem manterá os dados seguros, o que pode complicar o processo de conformidade com regulamentações de privacidade e segurança.

Apesar de todos esses riscos, tem se tornado cada vez mais comum as organizações construírem novas aplicações sobre serviços em nuvem ou adotarem uma abordagem híbrida, na qual serviços em nuvem são usados para alguns aspectos de um sistema. No entanto, os serviços em nuvem não substituirão todos os sistemas de dados internos. Muitos sistemas mais antigos são anteriores à nuvem e, para serviços com requisitos especializados que os serviços em nuvem existentes não conseguem atender, os sistemas internos permanecem necessários. Por exemplo, aplicações muito sensíveis à latência, como negociação de alta frequência (*high-frequency trading*), exigem controle total do hardware.

## Cloud Native System Architecture
Além de apresentar um modelo econômico diferente (assinar um serviço em vez de comprar hardware e licenciar software para executá-lo), a ascensão da nuvem também teve um efeito profundo na forma como os sistemas de dados são implementados em nível técnico. O termo *cloud native* é usado para descrever uma arquitetura projetada para aproveitar os serviços em nuvem.

Em princípios, quase qualquer software que possamos hospedar por conta própria (*self-host*) também poderia ser oferecido como um serviço em nuvem e, de fato, esses *managed services* já estão disponíveis para muitos sistemas de dados populares. No entanto, <span style="background:#fff88f">sistemas que foram projetados desde o início para serem</span> *cloud native* demonstraram ter várias vantagens: <span style="background:#d3f8b6">melhor desempenho no mesmo hardware</span>, <span style="background:#d3f8b6">recuperação mais rápida de falhas</span>, capacidade de <span style="background:#d3f8b6">dimensionar</span> rapidamente os recursos computacionais <span style="background:#d3f8b6">para acompanhar a carga e suporte a conjuntos de dados maiores</span>. A tabela 1-2 lista alguns exemplos de ambos os tipos de sistemas.

*Cloud Native* não é só migrar para a nuvem, mas arquitetar para elasticidade e resiliência nativas. 

!![image-20264205136353.png](/image-20264205136353.png)

**Layering of cloud services**
Muitos sistemas de dados auto-hospedados (*self-hosted*) possuem requisitos de sistema simples: eles rodam em um sistema operacional convencional, como Linux ou Windows, armazenam seus dados como arquivos no sistema de arquivos e se comunicam por meio de protocolos de rede padrão, como TCP/IP. Alguns sistemas dependem de hardware especializado, como GPUs ou interfaces de rede com acesso direto à memória remota (RDMA), mas no geral, o software auto-hospedado tende a usar recursos computacionais genéricos: CPUs, RAM, um sistema de arquivos e uma rede IP.

Na nuvem, esse tipo de software pode ser executado em um ambiente de IaaS, usando uma ou mais máquinas virtuais (VMs ou instâncias) com uma determinada alocação de CPUs, memória, disco e largura de banda de rede. Comparadas a máquinas físicas, as instâncias em nuvem podem ser provisionadas mais rapidamente e estão disponíveis em uma variedade maior de tamanhos, mas fora isso, são semelhantes a computadores tradicionais: podemos executar qualquer software nelas, mas nós somos responsáveis por administrá-las por conta própria.

Em contraste, a ideia central dos serviços *cloud native* não é apenas usar os recursos computacionais gerenciados pelo seu sistema operacional, mas também construir sobre serviços de nuvem de nível mais baixo para criar serviços de nível mais alto. Por exemplo:
- Serviços de armazenamento de objetos, como Amazon S3, Azure Blob Storage e Cloudflare R2, armazenam arquivos grandes. Eles oferecem APIs limitadas do que um sistema de arquivos típico (leituras e gravações básicas de arquivos), mas têm a vantagem de ocultar máquinas físicas subjacentes; o serviço distribui automaticamente os dados em várias máquinas, para que a gente não precise nos preocuparmos em ficar sem espaço em disco em nenhuma máquina específica. Mesmo que algumas máquinas ou seus discos falhem completamente, nenhum dado é perdido. 
- Muitos outros serviços são, por sua vez, construídos sobre armazenamento de objetos e outros serviços em nuvem. Por exemplo, o Snowflake é um banco de dados analítico baseado em nuvem (*data warehouse*) que depende do S3 para armazenamento de dados, e alguns outros serviços, por sua vez, são construídos sobre o Snowflake.

Como sempre acontece com abstrações na computação, não existe uma resposta única sobre o que devemos usar. Como regra geral, abstrações de nível mais alto tendem a ser mais orientadas a casos de uso específicos. Se nossas necessidades corresponderem às situações para as quais um sistema de nível mais alto foi projetado, usar o sistema existente provavelmente atenderá às nossas demandas com muito menos complicação do que construí-lo nós mesmo a partir de sistemas de nível mais baixo. 

Por outro lado, se nenhum sistema de alto nível atender às suas necessidades, construí-lo você mesmo a partir de componentes de nível mais baixo é a única opção.

**Separation of storage and compute**
Na computação tradicional, o armazenamento em disco é considerado durável (partimos do pressuposto de que, uma vez gravado em disco, o dado não será perdido). Para tolerar a falha de um disco rígido individual, o *RAID* (Redundant Array of Independent Disks) é frequentemente usado para manter cópias dos dados em vários discos conectados à mesma máquina. O *RAID* pode ser implementado em hardware ou em software pelo sistema operacional e é transparente para as aplicações que acessam o sistema de arquivos.

Na nuvem, as instâncias de computação (VMs) também podem ter discos locais conectados, mas os sistemas *cloud native* geralmente tratam esses discos mais como um *cache* efêmero e menos como armazenamento de longo prazo. Isso ocorre porque o disco local se torna inacessível se a instância associada falhar ou se for substituída por uma maior ou menos (em uma máquina física diferente) para se adaptar a mudanças na carga.

Como alternativa aos discos locais, os serviços em nuvem também oferecem armazenamento em disco virtual que pode ser desvinculado de uma instância e conectado a outra (por exemplo, Amazon EBS, *Azure Managed Disks* e *Persistent Disks* no Google Cloud). Tal disco virtual não é um disco físico, mas sim um serviço em nuvem fornecido por um conjunto separado de máquinas que emula o comportamento de um disco (um dispositivo de bloco, onde cada bloco tem tipicamente 4 KiB de tamanho). Essa tecnologia possibilita executar software tradicional baseado em disco na nuvem, mas a emolução do dispositivo de bloco introduz #overheads que podem ser evitados em sistemas projetados desde o início para a nuvem. O uso de discos virtuais também torna a aplicação muito sensível a falhas de rede, já que cada operação de I/O no dispositivo de bloco virtual é uma chamada de rede.

Para resolver esse problema, os serviços *cloud native* geralmente evitam o uso de discos virtuais e, em vez disso, constroem sobre serviços de armazenamento dedicados otimizados para cargas de trabalho especificas. Serviços de armazenamento de objetos, como o S3, são projetados para armazenamento de longo prazo de arquivos razoavelmente grandes, variando de centenas de quilobytes a vários gigabytes de tamanho. As linhas ou valores individuais armazenados em um banco de dados são tipicamente muito menores que isso; portanto, bancos de dados em nuvem geralmente gerenciam valores menores em um serviço separado e armazenam blocos de dados maiores (contendo muito svalores individuais) em um *object store*. Veremos formas de fazer isso no Capítulo 4.

Em uma arquitetura de sistemas tradicional, o mesmo computador é responsável tanto pelo armazenamento (disco) quanto pela computação (CPU e RAM), mas em sistemas *cloud native*, essas duas responsabilidades tornaram-se de certa forma separadas, ou *disaggregated*: por exemplo, o S3 apenas armazena arquivos e, se quisermos analisar esses dados, precisaremos executar o código de análise em algum lugar fora do S3. Isso implica transferir os dados pela rede, o que discutiremos mais adiante em *Sistemas Distribuídos versus Single-Node*.

Além disso, sistemas *cloud native* frequentemente são #multitenant, o que significa que, em vez de ter uma máquina separada para cada cliente, dados e computação de vários clientes são processados no mesmo hardware compartilhado pelo mesmo serviço. O #multitenancy pode permitir melhor utilização de hardware, escalabilidade mais fácil e gerenciamento simplificado pelo provedor de nuvem, mas também <span style="background:#d3f8b6">exige engenharia cuidadosa para garantir que a atividade de um cliente não afete o desempenho ou a segurança</span> do sistema para outros clientes.

## Operations in the Cloud Era
Tradicionalmente, as pessoas gerenciavam a infraestrutura de dados *server-side* de uma organização eram conhecidas como administradores de banco de dados (DBAs) ou administradores de sistemas (*sysadmins*). Mais recentemente, muitas organizações têm tentado integrar as funções de desenvolvimento de software e operações em equipes com responsabilidade compartilhada tanto por serviços de *backend* quanto por infraestrutura de dados; a filosofia DevOps tem guiado essa tendência. Os *Site Reliability Engineers (SREs)* são a implementação dessa ideia pelo Google.

O papel das operações é garantir que os serviços sejam entregues de forma confiável aos usuários (incluindo configuração de infraestrutura e *deploy* de aplicações) e assegurar um ambiente de produção estável (incluindo monitoramento e diagnóstico de quaisquer problemas que possam afetar a confiabilidade). Para sistemas auto-hospedados, as operações tradicionalmente envolvem uma quantidade significativa de trabalho no nível de máquinas individuais, como planejamento de capacidade (por exemplo, monitorar o espaço em disco disponível e adicionar mais discos antes que o espaço acabe), provisionamento de novas máquinas, movimentação de serviços de uma máquina para outra e instalação de *patches* do sistema operacional.

Muitos serviços em nuvem apresentam uma API que oculta as máquinas individuais que implementam o serviço. Por exemplo, o armazenamento em nuvem substitui discos ed tamanho fixo por cobrança baseada em uso *metered billing*, na qual podemos armazenar dados sem precisar planejar nossas necessidades de capacidade com antecedência e é cobrado com base no espaço utilizado. Além disso, muitos serviços em nuvem permanecem altamente disponíveis, mesmo quando máquinas individuais falham (consulte "Confiabilidade e Tolerância a Falhas").

Essa mudança de ênfase, de máquinas individuais para serviços, foi acompanhada por uma transformação no papel das operações. O objetivo de alto nível de fornecer um serviço confiável permanece o mesmo, mas os processos e as ferramentas evoluíram.

A filosofia *DevOps/SRE* coloca maior ênfase nos seguintes aspectos:
- Configurar automação, preferindo processos repetíveis em vez de tarefas manuais pontuais;
- Usar VMs e serviços efêmeros em vez de servidores de longa duração;
- Permitir atualizações frequentes de aplicações;
- Aprender com incidentes;
- Preservar o conhecimento da organização sobre o sistema, mesmo com a entrada e saída de pessoas.

Com a ascensão dos serviços em nuvem, ocorreu uma bifurcação de papéis. Equipe de operações em empresas de infraestrutura especializam-se nos detalhes de fornecer um serviço confiável para um grande número de clientes, enquanto os clientes do serviço dedicam o mínimo de tempo e esforço possível à infraestrutura.

Clientes de serviços em nuvem ainda precisam de operações, mas focam em aspectos diferentes, como escolher o serviço mais adequado para uma determinada tarefa, integrar serviços entre si e migrar de um serviço para outro. Embora a cobrança baseada em uso elimine a necessidade de planejamento de capacidade no sentido tradicional, ainda é importante saber quais recursos você está usando e para qual finalidade, para não desperdiçar dinheiro com recursos em nuvem desnecessários. O planejamento de capacidade torna-se planejamento financeiro, e a otimização de desempenho torna-se otimização de custos [36]. Além disso, serviços em nuvem possuem limites de recursos ou cotas (como o número máximo de processos que você pode executar simultaneamente), sobre os quais você precisa saber e se planejar antes de esbarrar neles [37].

Adotar um serviço em nuvem pode ser mais fácil e rápido do que provisionar e executar sua própria infraestrutura, embora você ainda precise aprender a usar o serviço e, talvez, contornar suas limitações. A integração entre serviços torna-se um desafio particular à medida que um número crescente de fornecedores oferece uma gama cada vez mais ampla de serviços em nuvem voltados para diferentes casos de uso [38, 39]. _ETL_ (consulte "Data Warehousing" na página 7) é apenas parte da história; serviços operacionais em nuvem também precisam ser integrados entre si. No momento, não dispomos de padrões para facilitar esse tipo de integração, então ela frequentemente envolve esforço manual significativo.

Outros aspectos operacionais que não podem ser totalmente terceirizados para serviços em nuvem incluem: <span style="background:#fff88f">manter a segurança de uma aplicação</span> e das bibliotecas que ela utiliza, <span style="background:#fff88f">gerenciar as interações</span> entre seus próprios serviços, <span style="background:#fff88f">monitorar a carga nos seus serviços</span> e <span style="background:#fff88f">investigar a causa de problemas</span>, como degradações de desempenho ou interrupções. Embora a nuvem esteja transformando o papel das operações, a necessidade de operações é tão grande quanto sempre foi.

## Distributed Versus Single-Node Systems
Um sistema que envolve várias máquinas se comunicando por meio de uma rede é chamado de **sistema distribuído**. Cada um dos processos participantes em um sistema distribuído é chamado de nó. Podemos querer usar esse tipo de sistema por vários motivos:

**Distribuição inerente**
Se uma aplicação envolve dois ou mais usuários interagindo, cada um usando seu próprio dispositivo, então o sistema é inevitavelmente distribuído: a comunicação entre os dispositivos precisará ocorrer por meio de uma rede. 

**Requisições entre serviços em nuvem**
Se os dados são armazenados em um serviço, mas processados em outro, esses dados devem ser transferidos pela rede de um serviço para o outro. Sistemas *cloud native* e *microsservices* são, portanto, distribuídos.

**Tolerância a falhas / alta disponibilidade**
Se a nossa aplicação precisa continuar funcionando mesmo que uma máquina (ou várias máquinas, ou a rede, ou um datacenter inteiro) saia do ar, podemos usar várias máquinas para obter redundância. Quando uma falha, outra pode assumir. 

**Escalabilidade**
Se o volume de dados ou os requisitos computacionais crescerem além do que uma única máquina pode lidar, podemos, potencialmente, distribuir a carga entre várias máquinas para obter redundância. 

**Latência**
Se temos usuários ao redor do mundo, podemos querer ter servidores em várias regiões globais para que cada usuário seja atendido por um servidor geograficamente próximo. Isso evita que os usuários precisam esperar pacotes de rede viajarem metade do mundo para responder às nossas solicitações. 

**Elasticidade**
Se a nossa aplicação tem picos de uso em alguns momentos e fica ociosa em outros, uma implantação em nuvem pode dimensionar para cima ou para baixo conforme a demanda, para que a gente <span style="background:#fff88f">pague apenas pelos recursos que estamos usando ativamente</span>. Isso é mais difícil em uma única máquina, que precisa ser provisionada para lidar com a carga máxima, mesmo em momentos em que é pouco utilizada.

**Hardware especializado**
Diferentes partes do sistema podem aproveitar diferentes tipos de hardware para se adequar à sua carga de trabalho. Por exemplo, um *object store* pode usar máquinas com muita CPUs, enquanto um sistema de análise dados pode usar máquinas com muita CPU e memória, mas sem discos, e um sistema de *machine learning* pode usar máquinas com GPUs (que são muito mais eficientes que CPUs para treinar redes neurais profundas e outras tarefas de ML).

**Conformidade legal**
Alguns países possuem leis de residência de dados que exigem que dados sobre pessoas em sua jurisdição sejam armazenados e processados geograficamente dentro desse país [40]. O escopo dessas regras varia — por exemplo, em alguns casos, aplica-se apenas a dados médicos ou financeiros, enquanto em outros é mais amplo. Um serviço com usuários em várias dessas jurisdições, portanto, precisará distribuir seus dados entre servidores em várias localidades.

**Sustentabilidade**
Se você tem flexibilidade sobre onde e quando executar suas tarefas, pode ser possível executá-las em um horário e local onde haja abundância de energia renovável disponível e evitar executá-las quando a rede elétrica estiver sobrecarregada. Isso pode reduzir suas emissões de carbono e permitir que você aproveite energia barata quando disponível [41, 42].

Esses motivos se aplicam tanto a serviços que você mesmo desenvolve (código de aplicação) quanto a serviços compostos por software _off-the-shelf_ (como bancos de dados).

## Problems with Distributed Systems
Sistemas distribuídos também têm desvantagens. Cada requisição e chamada de API que atravessa a rede precisa lidar com a possibilidade de falha. A rede pode ser interrompida, ou o serviço pode estar sobrecarregado ou travar e, portanto, qualquer requisição pode sofrer *timeout* sem receber uma resposta. Nesse caso, não sabemos se o serviço recebeu a requisição, e simplesmente reenviá-la pode não ser seguro. Discutiremos esses problemas em detalhes no Capítulo 9.

Embora as redes de datacenter sejam rápidas, fazer uma chamada para outro serviço ainda é extremamente mais lento do que chamar uma função no mesmo processo. Ao operar sobre grande volumes de dados, em vez de transferir os dados do armazenamento para uma máquina separada que os processa, pode ser mais rápido levar a computação até a máquina que já possui os dados. Mais nós nem sempre significam mais velocidade; em alguns casos, um programa simples de thread única em um computador pode ter desempenho significativamente melhor do que um *cluster* com mais de 100 núcleos de CPU.

Solucionar problemas em um sistema distribuído costumar ser difícil, se o sistema está lento para responder, como descobrir onde está o problema? Técnicas para diagnosticar problemas em sistemas distribuídos são desenvolvidas sob o conceito de **observabilidade**, que envolve coletar dados sobre a execução de um sistema e permitir que esses dados sejam consultados de formas que possibilitam a análise tanto de métricas de alto nível quanto de eventos individuais. Ferramentas de *tracing* como OpenTelemetry, Zipkin e Jaeger permitem rasrear qual cliente chamou qual servidor para qual operação e quanto tempo cada chamada levou. 

Bancos de dados fornecem vários mecanismos para garantir consistências de dados, como veremos no Capítulos 6 e 8. No entanto, quando cada serviço possui seu próprio banco de dados, manter a consistência dos dados entre esses diferentes serviços torna-se um problema da aplicação. *Distributed transactions*, que exploramos no Capítulo 8, são uma técnica possível para garantir consistência, mas raramente são usadas em um contexto de *microservices* porque vão contra o objetivo de tornar os serviços independentes uns dos outros, e muitos bancos de dados não as suportam.

Por todos esses motivos, executar uma tarefa em uma única máquina costuma ser muito mais simples e barato do que configurar um sistema distribuído. CPUs, memória e discos tornaram-se maiores, mais rápidos e mais confiáveis. Quando combinados com bancos de dados *single-node* como DuckDB, SQLite, KùzuDB, muitas cargas de trabalho agora podem ser executadas em um único nó. Exploraremos esse tópico com mais detalhes no Capítulo 4.

## Microservices and Serverless
A forma mais comum de distribuir um sistema entre várias máquinas é dividi-lo em clientes e servidores, permitindo que os clientes façam requisições aos servidores. Na maioria dos casos, o HTTP é usado para essa comunicação, como discutiremos em "Fluxo de Dados por Serviços: REST e RPC" na página 180. O mesmo processo pode atuar tanto como servidor (tratando requisições recebidas) quanto como cliente (fazendo requisições de saída para outros serviços).

Essa forma de construir aplicações era tradicionalmente chamada de **arquitetura orientada a serviços (SOA)**; mais recentemente, a ideia foi refinada na **arquitetura de microsserviços**. Em uma arquitetura de microsserviços, um serviço tem um propósito bem definido (por exemplo, no caso do S3, é o armazenamento de arquivos); cada serviço expõe uma API que pode ser chamada por clientes pela rede, e cada serviço possui uma equipe responsável por sua manutenção. Assim, uma aplicação complexa pode ser decomposta em múltiplos serviços integrantes, cada um gerenciado por uma equipe separada. Sistemas *cloud native* fazem uso intensivo da decomposição em serviços, mas sistemas *on-premises* também podem adotar uma abordagem orientada a serviços.

Dividir um software complexo em múltiplos serviços traz várias vantagens: cada serviço pode ser atualizado independentemente, reduzindo o esforço de coordenação entre equipes; cada serviço pode receber os recursos de hardware que necessita; e ocultar os detalhes de implementação por trás de uma API significa que os proprietários do serviço têm liberdade para alterar a implementação sem afetar os clientes. Em termos de armazenamento de dados, é comum que cada serviço tenha seus próprios bancos de dados, sem compartilhamento entre serviços. Compartilhar um banco de dados efetivamente tornaria toda a estrutura do banco parte da API do serviço, dificultando alterações futuras. Bancos compartilhados também poderiam fazer com que as consultas de um serviço impactassem negativamente o desempenho de outros.

Por outro lado, ter muito serviços pode, por si só, gerar complexidade. Testar um serviço durante o desenvolvimento pode ser complicado, pois é necessário executar também todos os outros serviços dos quais ele depende. Além disso, cada serviço exige infraestrutura para implantar novas versões, ajustar os recursos de hardware alocados conforme a carga, coletar *logs*, monitorar a saúde do serviço e alertar um engenheiro de plantão em caso de problemas. *Frameworks* de orquestração, como o Kubernetes, tornaram-se uma forma popular de implantar serviços, pois fornecem a base para essa infraestrutura.

Além disso, as *APIs* de microsserviços podem ser desafiadoras para evoluir. Clientes que chamam uma *API* esperam que ela tenha determinados campos. Desenvolvedores podem querer adicionar ou remover campos em uma API conforme as necessidades de negócio mudam, mas isso pode causar falhas nos clientes. Pior ainda, essas falhas muitas vezes só são descobertas tardiamente no ciclo de desenvolvimento, quando a API atualizada do serviço é implantada em um ambiente de *stagging* ou produção. Padrões de descrição de *API*, como OpenAPI e gRPC, ajudam a gerenciar a relação entre as APIs de cliente e servidor; discutimos isso com mais detalhes no Capítulo 5. 

Os microsserviços são, principalmente, uma solução técnica para um problema de pessoas: permitir que diferentes equipes avancem de forma independente, sem necessidade de coordenação mútua. Isso é valioso em uma grande empresa, mas, em uma empresa pequena com menos equipes, usar microsserviços provavelmente será um *overhead* desnecessário, sendo preferível implementar a aplicação de forma mais simples possível.

O *Serverless*, ou *Function as a Service (FaaS)*, é outra abordagem para implantar serviços, na qual o gerenciamento da infraestrutura é terceirizado para um provedor de nuvem. Ao usar VMs, precisamos escolher explicitamente quando iniciar ou desligar uma instância; em contraste, no modelo *serverless*, o provedor de nuvem aloca e libera automaticamente os recursos de hardware conforme necessário, com base nas requisições recebidas pelo seu serviço. Assim como o armazenamento em nuvem substituiu o planejamento de capacidade (decidir antecipadamente quantos discos comrpar) por um modelo de cobrança por uso, a abordagem *serverless* está trazendo a cobrança por uso para a execução de código: pagamos apenas pelo tempo em que o código da nossa aplicação está em execução, em vez de precisar provisionar recursos antecipadamente.

Para oferecer esse benefícios, muitos provedores de infraestrutura *serverless* impõem um limite de tempo para a execução de funções e restringem os ambientes de *runtime*, e os serviços podem sofrer com tempos de inicialização lentos quando uma função é invocada pela primeira vez. O termo *"serverless"* também pode ser enganoso; cada execução de função *serverless* ainda roda em um servidor, mas execuções subsequentes podem ocorrer em um servidor diferente. Além disso, serviços de infraestrutura, como o BigQuery e diversas ofertas de Kafka, adotaram a terminologia "serverless" para sinalizar que seus serviços possuem escalonamento automático (*autoscale*) e cobram pelo uso, e não por instâncias de máquina.

## Cloud Computing Versus Supercomputing
A computação em nuvem não é a única forma de construir sistemas de computação em larga escala; uma alternativa é a **computação de alto desempenho** (*High-Performance Computing - HPC*), também conhecida como *supercomputing*. Embora existam sobreposições, o HPC frequentemente possui prioridades diferentes e utiliza técnicas distintas em comparação com a computação em nuvem e sistemas de datacenter corporativos. Abaixo estão algumas das principais diferenças:
- Supercomputadores são tipicamente usados para tarefas de computação científica intensivas em processamento, como previsão do tempo, modelagem climática, dinâmica molecular (simulação do movimento de átomos e moléculas), problemas complexos de otimização e resolução de equações diferenciais parciais. Por outro lado, a computação em nuvem tende a ser usada para serviços online, sistemas de dados empresariais e sistemas similares que precisam atender requisições de usuários com alta disponibilidade.
- Um supercomputador tipicamente executa grandes **batch jobs** que salvam o estado de sua computação em disco periodicamente (*checkpointing*). Se um nó falha, uma solução comum é simplesmente parar toda a carga de trabalho do *cluster*, reparar o nó com falha e reiniciar a computação a partir do último *checkpoint*. Com serviços em nuvem, para o *cluster* inteiro geralmente não é desejável, pois os serviços precisam atender usuários continuamente, com interrupções mínimas. 
- Nós de supercomputadores tipicamente se comunicam por meio de memória compartilhada e RDMA, que suportam alta largura de banda e baixa latência, mas assumem um alto nível de confiança entre os usuários do sistema. Na computação em nuvem, a rede e as máquinas são frequentemente compartilhadas por organizações que não confiam umas nas outras, exigindo mecanismos de segurança mais robustos, como isolamento de recursos (por exemplo, máquinas virtuais), criptografia e autenticação.
- Redes de datacenter em nuvem são frequentemente baseadas em IP e Ethernet, organizadas em topologias *Clos* para fornecer alta largura de banda de *bisection*, uma medida comumente usada para o desempenho geral de uma rede. Supercomputadores frequentemente usam topologias de rede especializadas, como *meshes* multidimensionais e *toruses*, que oferecem melhor desempenho para cargas de trabalho de HPC com padrões de comunicação conhecidos.
- A computação em nuvem permite que nós sejam distribuídos por múltiplas regiões geográficas, enquanto supercomputadores geralmente assumem que os seus nós estão próximos fisicamente.

Sistemas analíticos em larga escala às vezes compartilham algumas características com a supercomputação, razão pelo qual pode valer a pena conhecer essas técnicas se trabalhamos nessa área. 

## Data Systems, Law, and Society
Como você viu neste capítulo, a arquitetura de sistemas de dados é influenciada não apenas por objetivos e requisitos técnicos, mas também pelas necessidades humanas das organizações que eles suportam. Cada vez mais, engenheiros de sistemas de dados estão percebendo que atender às necessidades de seu próprio negócio não é suficiente; também temos uma responsabilidade para com a sociedade em geral.

Uma preocupação particular são os sistemas que armazenam dados sobre pessoas e seu comportamento. Desde 2018, o **GDPR** concede aos residentes de muitos países europeus maior controle e direitos legais sobre seus dados pessoais, e regulamentações similares de privacidade foram adotadas em vários outros países e estados ao redor do mundo (incluindo, por exemplo, a **CCPA**). Regulamentações sobre _AI_, como o **EU AI Act**, impõem restrições adicionais sobre como dados pessoais podem ser utilizados.

Além disso, mesmo em áreas que não estão diretamente sujeitas a regulamentação, há um reconhecimento crescente dos efeitos que os sistemas de computação têm sobre as pessoas e a sociedade. As redes sociais mudaram a forma como os indivíduos consomem notícias, o que influencia suas opiniões políticas e, consequentemente, pode afetar o resultado de eleições. Sistemas automatizados tomam decisões cada vez mais impactantes para os indivíduos, como quem deve receber um empréstimo ou cobertura de seguro, quem deve ser convidado para uma entrevista de emprego ou quem deve ser suspeito de um crime [59].

Todos os que trabalham nesses sistemas compartilham a responsabilidade de considerar o impacto ético de suas decisões e garantir que estejam em conformidade com as leis relevantes. Nem todos precisam se tornar especialistas em direito e ética, mas uma conscientização básica sobre princípios legais e éticos é tão importante quanto, digamos, algum conhecimento fundamental em sistemas distribuídos.

Considerações legais estão influenciando os próprios fundamentos do design de sistemas de dados [60]. Por exemplo, o GDPR concede aos indivíduos o direito de ter seus dados apagados mediante solicitação (conhecido às vezes como _right to be forgotten_). No entanto, como veremos neste livro, muitos sistemas de dados dependem de construções imutáveis, como _logs_ do tipo _append-only_, como parte de seu design. Como podemos garantir a exclusão de alguns dados no meio de um arquivo que deveria ser imutável? Como lidamos com a exclusão de dados que foram incorporados a conjuntos de dados derivados (consulte "Sistemas de Registro e Dados Derivados" na página 10), como dados de treinamento para modelos de _ML_? Responder a essas questões cria novos desafios de engenharia.

No momento, não temos diretrizes claras sobre quais tecnologias ou arquiteturas de sistema específicas devem ser consideradas em conformidade com o GDPR. A regulamentação deliberadamente não exige tecnologias específicas, pois estas podem mudar rapidamente com o avanço da tecnologia. Em vez disso, os textos legais estabelecem princípios de alto nível sujeitos a interpretação. Portanto, como cumprir regulamentações de privacidade não tem uma resposta simples, mas examinaremos algumas das tecnologias sob essa perspectiva.

De modo geral, armazenamos dados porque acreditamos que seu valor é maior que os custos de armazená-los. No entanto, vale lembrar que os custos de armazenamento vão além da fatura que você paga pelo S3 ou outro serviço. O cálculo de custo-benefício também deve levar em conta os riscos de responsabilidade civil e danos à reputação se os dados vazarem ou forem comprometidos por adversários, e o risco de custos legais e multas se o armazenamento e processamento dos dados forem considerados em desacordo com a lei [50]. Governos ou forças policiais também podem obrigar empresas a entregar dados.

Quando os dados podem revelar comportamentos criminalizados (por exemplo, homossexualidade em vários países do Oriente Médio e da África, ou a busca por um aborto em vários estados dos Estados Unidos), armazenar esses dados cria riscos reais de segurança para os usuários. Uma viagem a uma clínica de aborto, por exemplo, poderia ser facilmente revelada por dados de localização ou talvez até por um _log_ dos endereços IP do usuário ao longo do tempo (que indicam localização aproximada).

Uma vez que todos os riscos são considerados, pode ser razoável decidir que alguns dados simplesmente não valem a pena ser armazenados e, portanto, devem ser excluídos. Esse princípio de **minimização de dados** (conhecido às vezes pelo termo alemão _Datensparsamkeit_) vai contra a filosofia do "_big data_" de armazenar muitos dados de forma especulativa, caso venham a ser úteis no futuro [61]. Mas a minimização de dados se alinha ao GDPR, que determina que dados pessoais só podem ser coletados para um propósito específico e explícito; não podem ser usados posteriormente para qualquer outro fim; e não devem ser mantidos por mais tempo do que o necessário para os propósitos para os quais foram coletados [62].

Empresas também têm observado preocupações com privacidade e segurança. Empresas de cartão de crédito exigem que processadores de pagamento aderam a padrões rigorosos do _Payment Card Industry_ (PCI). Processadores passam por avaliações frequentes de auditores independentes para verificar a conformidade contínua. Fornecedores de software também têm visto maior escrutínio. Muitos compradores agora exigem que seus fornecedores cumpram os padrões _Service Organization Control_ (SOC) Type 2. Assim como na conformidade com PCI, fornecedores passam por auditorias de terceiros para verificar a adesão.

De modo geral, é importante equilibrar as necessidades do seu negócio com as necessidades das pessoas cujos dados você está coletando e processando. Há muito mais a dizer sobre este tópico; no Capítulo 14, vamos nos aprofundar em ética e conformidade legal, incluindo os problemas de viés e discriminação.

Privacidade e ética são requisitos de arquitetura, não apenas jurídicos: _data minimization_, exclusão em sistemas imutáveis e proteção de dados sensíveis exigem decisões de design conscientes. Armazenar menos pode reduzir risco legal, reputacional e humano — e ainda economizar custos.

O tema deste capítulo foi compreender _trade-offs_ — ou seja, reconhecer que muitas perguntas não têm uma única resposta correta, mas várias possibilidades, cada uma com seus prós e contras. Exploramos algumas das escolhas mais importantes que afetam a arquitetura de sistemas de dados e introduzimos terminologia que será utilizada ao longo do restante deste livro.

Começamos distinguindo entre <span style="background:#fff88f">sistemas operacionais</span> (processamento de transações, _OLTP_) e analíticos (_OLAP_) e explorando como eles diferem, não apenas no gerenciamento de tipos distintos de dados com padrões de acesso diferentes, mas também no atendimento a públicos distintos. No caminho, encontramos os conceitos de _data warehouse_ e _data lake_, que recebem fluxos de dados de sistemas operacionais por meio de _ETL_. No Capítulo 4, veremos que sistemas operacionais e analíticos frequentemente usam layouts de dados internos muito diferentes devido aos tipos distintos de consultas que precisam atender.

Em seguida, comparamos serviços em nuvem — um desenvolvimento relativamente recente — ao paradigma tradicional de software auto-hospedado (_self-hosted_), que anteriormente dominava a arquitetura de sistemas de dados. Qual dessas abordagens é mais custo-efetiva depende muito da sua situação específica, mas é inegável que as abordagens _cloud native_ estão trazendo grandes mudanças à forma como os sistemas de dados são arquitetados — por exemplo, na maneira como separam armazenamento e computação.

Sistemas em nuvem são intrinsecamente distribuídos, e examinamos brevemente alguns dos _trade-offs_ de sistemas distribuídos em comparação ao uso de uma única máquina. Em algumas situações, não é possível evitar a distribuição, mas é aconselhável não apressar a decisão de tornar um sistema distribuído se for possível mantê-lo em uma única máquina. No Capítulo 9, abordaremos os desafios dos sistemas distribuídos com mais detalhes.

Por fim, vimos que a arquitetura de um sistema de dados é determinada não apenas pelas necessidades do negócio que o implanta, <span style="background:#d3f8b6">mas também por regulamentações de privacidade que protegem os direitos das pessoas cujos dados estão sendo processados</span> — um aspecto que muitos engenheiros tendem a ignorar. Como traduzir requisitos legais em implementações técnicas ainda não foi formalizado, mas é importante manter essa questão em mente à medida que avançamos pelo restante deste livro.
