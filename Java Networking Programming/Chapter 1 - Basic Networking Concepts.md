## Networks
Uma rede é uma coleção de computadores e outros dispositivos que podem enviar e receber dados entre si, mais ou menos em tempo real. Uma rede é frequentemente conectada por fios, e os *bits* de dados são transformados em ondas eletromagnéticas que se movem através desses fios. No entanto, as redes sem fio transmitem dados usando ondas de rádio; e a maioria das transmissões de longa distância agora é transportada por cabos de fibra óptica que enviam ondas de luz através de filamentos de vidro. <span style="background:#fff88f">Não existe nenhuma obrigatoriedade quanto a um meio físico específico para a transmissão de dados.</span> Teoricamente, os dados podem ser transmitidos por computadores movidos a carvão que enviassem sinais de fumaça uns aos outros. O tempo de resposta (e o impacto ambiental) de uma rede desse tipo seria bastante ruim.

Cada máquina em uma rede é chamada de nó (node). A maioria dos nós são computadores, mas impressoras, roteadores, *bridges*, gateways, terminais burros e máquinas da Coca-cola também podem ser nós. Podemos usar o Java para fazer a interface com uma máquina de Coca-cola, mas, de mogo geral, comunicaremos com outros computadores. Os nós que são computadores totalmente funcionais também são chamados de *hosts* (hospedeiros). Usarei a palavra nó para nos referirmos a qualquer dispositivo na rede, e a palavra host para me referir a um nó que seja um computador de uso geral.

Cada nó da rede possui um endereço, uma sequência de #bytes que o identifica de forma única. Podemos pensar nesse grupo de bytes como um número, mas em geral, o número de bytes em um endereço ou a ordenação desses bytes (big endian ou little endian) não tem garantia de corresponder a nenhum tipo de dado numérico primitivo em Java. Quanto mais bytes houver em cada endereço, mais endereços estarão disponíveis e mais dispositivos poderão ser conectados à rede simultaneamente.

Os endereços são atribuídos de maneira diferente em diferentes tipos de redes. Os endereços Ethernet estão atrelados ao hardware físico Ethernet. Os fabricantes de *hardware* Ethernet usam códigos de fabricante pré-atribuídos para que não haja conflitos entre os endereços em seus equipamentos e os endereços dos equipamentos de outros fabricantes. Cada fabricante é responsável por garantir que não envie duas placas Ethernet com o mesmo endereço. Os endereços de Internet são normalmente atribuídos a um computador pela organização responsável por ele. No entanto, os endereços que uma organização tem permissão para escolher para seus computadores são atribuídos pelo provedor de serviços de Internet (ISP) da organização. Os ISPs obtêm seus endereços IP de um dos quatro registros regionais de Internet (o registro para a América do Norte é o ARIN, _American Registry for Internet Numbers_), que, por sua vez, recebem endereços IP atribuídos pela Corporação da Internet para Atribuição de Nomes e Números (ICANN).
Em alguns tipos de redes, os nós também possuem nomes de texto que ajudam os seres humanos a identificá-los, como “[www.elharo.com](https://www.elharo.com)” ou “Computador da Beth Harold”. Em um determinado momento, um nome específico normalmente se refere a exatamente um endereço. No entanto, os nomes não estão fixos aos endereços. Os nomes podem mudar enquanto os endereços permanecem os mesmos; da mesma forma, os endereços podem mudar enquanto os nomes permanecem os mesmos. Um endereço pode ter vários nomes e um nome pode se referir a vários endereços diferentes.

Todas as redes de computadores modernas são redes de comutação de pacotes (_packet-switched networks_): os dados que viajam na rede são divididos em pedaços chamados pacotes, e cada pacote é tratado separadamente. <span style="background:#fff88f">Cada pacote contém informações sobre quem o enviou e para onde ele está indo.</span> A vantagem mais importante de quebrar os dados em pacotes endereçados individualmente é que pacotes de muitas trocas contínuas podem viajar em um único fio, o que torna a construção de uma rede muito mais barata: muitos computadores podem compartilhar o mesmo fio sem interferência.

(Em contraste, quando você faz uma chamada telefônica local dentro da mesma central em uma linha telefônica tradicional, você essencialmente reserva um fio do seu telefone para o telefone da pessoa para quem está ligando. Quando todos os fios estão em uso, como às vezes acontece durante uma grande emergência ou feriado, nem todo mundo que pega o telefone terá um sinal de linha. Se você continuar na linha, eventualmente terá um sinal quando uma linha for liberada. Em alguns países com serviço telefônico pior do que os Estados Unidos, não é incomum ter que esperar meia hora ou mais por um sinal de linha). Outra vantagem dos pacotes é que as somas de verificação (_checksums_) podem ser usadas para detectar se um pacote foi danificado durante o trânsito.

Ainda nos falta uma peça importante: alguma noção do que os computadores precisam dizer para passar os dados de um lado para o outro. Um <span style="background:#fff88f">protocolo é um conjunto preciso de regras que define como os computadores se comunicam</span>: o formato dos endereços, como os dados são divididos em pacotes e assim por diante. Existem muitos protocolos diferentes que definem diferentes aspectos da comunicação de rede. Por exemplo, o Protocolo de Transferência de Hipertexto (HTTP) define como os navegadores web e os servidores se comunicam; no outro extremo do espectro, o padrão IEEE 802.3 define um protocolo de como os _bits_ são codificados como sinais elétricos em um tipo específico de cabo. Padrões de protocolo abertos e publicados permitem que _softwares_ e equipamentos de diferentes fornecedores se comuniquem entre si. Um servidor web não se importa se o cliente é uma estação de trabalho Unix, um celular Android ou um iPad, porque todos os clientes falam o mesmo protocolo HTTP, independentemente da plataforma.
## The Layers of a Network
O envio de dados através de uma rede é uma operação complexo que deve ser cuidadosamente ajustada às características físicas da rede, bem como ao caráter lógico dos dados que estão sendo enviados. O software que envia dados por uma rede deve entender como evitar colisões entre pacotes, converter dados digitais em sinais analógicos, detectar e corrigir erros, rotear pacotes de um *host* para outro e muito mais. O processo se torna ainda mais complicado quando se adiciona o requisito de suportar vários sistemas operacionais e cabeamentos de rede heterogêneos.

Para esconder a maior parte dessa complexidade do desenvolvedor de aplicativos e do usuário final, os diferentes aspectos da comunicação de rede são separados em múltiplas camadas. Cada camada representa um nível diferente de abstração entre o _hardware_ físico (ou seja, os fios e a eletricidade) e as informações que estão sendo transmitidas. Na teoria, cada camada se comunica apenas com as camadas imediatamente acima e imediatamente abaixo dela. A separação da rede em camadas permite modificar ou até mesmo substituir o _software_ de uma camada sem afetar as outras, desde que as interfaces entre as camadas permaneçam as mesmas.

Embora os protocolos da camada intermediária sejam bastante consistente na maior parte da Internet hoje, o topo e a base variam muito. Alguns *hosts* usam Ethernet; alguns usam Wi-Fi; alguns usam PPP; alguns usam outra coisa. Da mesma forma, o que está no topo da pilha dependerá completamente de quais programas o *host*  está executando. O ponto principal é que, do topo da pilha, não importa realmente o que está na base e vice-versa. O modelo de camada desacopla os protocolos de aplicação (o assunto principal deste livro) da física do *hardware* de rede e da topologia das conexões de rede.

Por exemplo, quando um navegador web envia uma solicitação a um servidor web para recuperar uma página, o navegador estará, na verdade, falando com a camada de transporte na máquina cliente local. A camada de transporte divide a solicitação em segmentos TCP, adiciona alguns números de sequência e somas de verificação *chechksums* aos dados e, em seguida, passa a solicitação para a camada de internet local. A camada de internet fragmenta os segmentos em datagramas IP do tamanho necessário para a rede local e os passa para a camada de host-para-rede (host-to-network) para a transmissão pelo cabo. A camada de host-para-rede codifica os dados digitais como sinais analógicos apropriados para o meio físico específico e envia a solicitação pelo cabo, onde será lida pela camada de host-para-rede do sistema ao qual está endereçada.

A camada de host-para-rede no sistema remoto decodifica os sinais analógicos em dados digitais e, em seguida, passa os datagramas IP resultantes para a camada de internet do servidor. A camada de internet faz algumas verificações simples para ver se os datagramas IP não estão corrompidos, remonta-os se tiverem sido fragmentados e os passa para a camada de transporte do servidor. A camada de transporte do servidor verifica se todos os dados chegaram e solicita a retransmissão de quaisquer partes ausentes ou corrompidas. (Essa solicitação, na verdade, desce de volta pela camada de internet do servidor, pela camada de host-para-rede do servidor e retorna ao sistema cliente, onde sobe novamente para a camada de transporte do cliente, que retransmite os dados ausentes de volta pelas camadas. Tudo isso é transparente para a camada de aplicação). Assim que a camada de transporte do servidor recebe datagramas contíguos e sequenciais suficientes, ela os remonta e os escreve em um fluxo (_stream_) lido pelo servidor web em execução na camada de aplicação do servidor. O servidor responde à solicitação e envia sua resposta de volta através das camadas no sistema do servidor para transmissão de volta pela Internet e entrega ao cliente web.

Como você pode imaginar, o processo real é muito mais elaborado. A camada de host-para-rede é de longe a mais complexa, e muita coisa foi deliberadamente ocultada. Por exemplo, é perfeitamente possível que os dados enviados pela Internet passem por vários roteadores e suas camadas antes de chegarem ao seu destino final. Pode ser necessário convertê-los de ondas de rádio no ar para sinais elétricos em fios de cobre, para pulsos de luz em cabos de fibra óptica e vice-versa, possivelmente mais de uma vez. No entanto, em 90% do tempo, seu código Java funcionará na camada de aplicação e só precisará falar com a camada de transporte. Nos outros 10% do tempo, você estará na camada de transporte e falando com a camada de aplicação ou com a camada de internet. A complexidade da camada de host-para-rede fica oculta de você; esse é o objetivo do modelo de camadas.

Se você ler a literatura sobre redes, é provável que encontre um modelo alternativo de sete camadas chamado Modelo de Referência de Interconexão de Sistemas Abertos (OSI). Para programas de rede em Java, o modelo OSI é um exagero. A maior diferença entre o modelo OSI e o modelo TCP/IP usado neste livro é que o modelo OSI divide a camada de host-para-rede nas camadas de enlace de dados e física, e insere as camadas de apresentação e sessão entre as camadas de aplicação e de transporte. O modelo OSI é mais geral e mais adequado para redes não TCP/IP, embora, na maioria das vezes, ainda seja excessivamente complexo. De qualquer forma, as classes de rede do Java funcionam apenas em redes TCP/IP e sempre nas camadas de aplicação ou de transporte, portanto, para os propósitos deste livro, absolutamente nada se ganha usando o modelo OSI, que é mais complicado.

Para a camada de aplicação, parece que ela está falando diretamente com a camada de aplicação no outro sistema; a rede cria um caminho lógico entre as duas camadas de aplicação _(como ilustrado na Figura 1-2 enviada por você)_. É fácil entender o caminho lógico se você pensar em uma sessão de bate-papo no IRC. A maioria dos participantes de um bate-papo no IRC diria que está falando com outra pessoa. Se você realmente os pressionar, eles podem dizer que estão falando com o computador deles (na verdade, a camada de aplicação), que está falando com o computador da outra pessoa, que está falando com a outra pessoa. Tudo que tem mais de uma camada de profundidade é efetivamente invisível, e é exatamente assim que deve ser. Vamos considerar cada camada com mais detalhes.

## The Host-to-Network Layer
Como programador Java, você está bem no alto da cadeia alimentar das redes. Muita coisa acontece fora do seu radar. No modelo de referência padrão para Internets baseadas em IP (o único tipo de rede que o Java realmente entende), as partes ocultas da rede pertencem à camada _host-to-network_ (também conhecida como camada de enlace, camada de enlace de dados ou camada de interface de rede).

A camada _host-to-network_ define como uma interface de rede específica — como uma placa Ethernet ou uma antena Wi-Fi — envia datagramas IP por meio de sua conexão física para a rede local e para o mundo.

A parte da camada _host-to-network_ composta pelo _hardware_ que conecta diferentes computadores (fios, cabos de fibra óptica, ondas de rádio ou sinais de fumaça) às vezes é chamada de camada física da rede. Como programador Java, você não precisa se preocupar com essa camada, a menos que algo dê errado — o cabo desconecte da parte de trás do seu computador, ou alguém passe com uma retroescavadeira por cima da linha T-1 entre você e o resto do mundo. Em outras palavras, o Java nunca enxerga a camada física.

O principal motivo pelo qual você precisará pensar sobre a camada _host-to-network_ e a camada física, se é que precisará pensar nelas, é o desempenho. Por exemplo, se seus clientes residem em conexões de fibra óptica rápidas e confiáveis, você projetará seu protocolo e seus aplicativos de forma diferente do que se eles estivessem em conexões de satélite de alta latência em uma plataforma de petróleo no Mar do Norte. Você fará escolhas ainda mais diferentes se seus clientes estiverem em um plano de dados 3G, onde são cobrados por _byte_ por uma largura de banda relativamente baixa. E se você estiver escrevendo um aplicativo de consumo geral que possa ser usado por qualquer um desses clientes, tentará encontrar um ponto de equilíbrio no meio do caminho, ou talvez até mesmo detectar e se adaptar dinamicamente aos recursos individuais do cliente. No entanto, independentemente dos links físicos que você encontrar, as APIs que você usa para se comunicar por meio dessas redes são as mesmas. O que torna isso possível é a camada de internet.

## A Camada de Internet
A próxima camada de rede, e a primeira com a qual precisamos nos preocupar, é a camada de internet. No modelo OSI, a camada de internet atende pelo nome mais genérico de camada de rede. Um protocolo de camada de rede define como os _bits_ e _bytes_ de dados são organizados em grupos maiores chamados pacotes, e o esquema de endereçamento pelo qual diferentes máquinas se encontram. O Protocolo de Internet (IP) é o protocolo de camada de rede <span style="background:#fff88f">mais utilizado no mundo</span> e o único protocolo de camada de rede que o Java entende.

> Dizer que o "Java enxerga o protocolo IP" significa que as abstrações de rede fornecidas pela linguagem foram projetadas exclusivamente para funcionar em cima da pilha de protocolos TCP/IP (que inclui o IP na camada de rede).

**Como o Java "enxerga" o IP?**
O Java não interage diretamente com a placa de rede ou com os cabos. Em vez disso, ele se comunica com o Sistema Operacional por meio de uma interface chamada **Socket API** (baseada nos *Berkeley Sockets* do Unix).

Quando usamos classes do Java como *Socket*, *ServerSocket*, #DatagramSocket ou #InetAddress, o Java está, por baixo dos panos, pedindo ao sistema Operacional para criar uma conexão de rede. Como todos os sistemas operacionais modernos usam o TCP/IP como padrão, o Java assume e exige que os endereços e roteamentos sejam feitos via IP (seja IPv4 ou IPv6).

Por exemplo, a classe #InetAddress é a representação Java de um endereço IP. Não existe uma classe padrão no Java para representar um endereço MAC (Camada 2) ou um endereço de protocolos antigos como IPX/SPX.

O Java foi, na verdade, **pioneiro** nessa abordagem. Quando foi criado em meados dos anos 90, ele já nasceu com a Internet em seu DNA, ignorando protocolos legados e apostando tudo no TCP/IP.

Historicamente, o Java foi criado na era em que a Internet (e, portanto, o TCP/IP) estava se tornando o padrão global. Os engenheiros da Sun Microsystems (criadora do Java) projetaram a API `java.net` focando 100% no modelo TCP/IP.

Para o Java, toda a comunicação de rede começa e termina com um endereço IP e uma porta, delegando todo o trabalho de roteamento e entrega de pacotes ao sistema operacional subjacente, que também é baseado em IP.

Na verdade, são dois os protocolos: o IPv4, que usa endereços de 32 bits, e o IPv6, que usa endereços de 128 bits e adiciona alguns outros recursos técnicos para auxiliar no roteamento. No momento em que este livro foi escrito, o IPv4 ainda representa mais de 90% do tráfego da Internet, mas o IPv6 está se popularizando rapidamente e pode muito bem ultrapassar o IPv4 antes da próxima edição do livro. Embora esses sejam dois protocolos de rede muito diferentes que não interoperam na mesma rede sem _gateways_ especiais e/ou protocolos de tunelamento, o Java oculta quase todas as diferenças para você.

Tanto no IPv4 quanto no IPv6, o<span style="background:#fff88f">s dados são enviados através da camada de internet</span> em <span style="background:#d3f8b6">pacotes</span> chamados #datagramas. Cada datagrama IPv4 contém um cabeçalho com entre 20 e 60 _bytes_ de comprimento e uma carga útil (_payload_) que contém até 65.515 _bytes_ de dados. (Na prática, a maioria dos datagramas IPv4 é muito menor, variando de algumas dezenas de _bytes_ a pouco mais de oito _kilobytes_). Um datagrama IPv6 contém um cabeçalho maior e até quatro _gigabytes_ de dados.

A Figura 1-3 mostra como as diferentes quantidades são arranjadas em um datagrama IPv4. Todos os _bits_ e _bytes_ são _big endian_; do mais significativo ao menos significativo, ordenados da esquerda para a direita.

Além de roteamento e endereçamento, o segundo objetivo da camada de Internet é permitir que diferentes tipos de camadas _Host-to-Network_ conversem entre si. Roteadores de Internet traduzem entre Wi-Fi e Ethernet, Ethernet e DSL, protocolos de _backhaul_ DSL e de fibra óptica, e assim por diante. Sem a camada de internet ou algo parecido, cada computador só conseguiria conversar com outros computadores que compartilhassem o seu tipo específico de rede. A camada de internet é responsável por conectar redes heterogêneas entre si usando protocolos homogêneos.

> A estatística do IPv4 também está defasada; hoje, a adoção global do IPv6 já ultrapassa a marca de 40%.

### A Camada de Transporte
Datagramas brutos têm algumas desvantagens. Mais notavelmente, não há garantia de que serão entregues. Mesmo que sejam entregues, podem ter sido corrompidos durante o trânsito. A soma de verificação (_checksum_) do cabeçalho só pode detectar corrupção no cabeçalho, não na parte de dados de um datagrama. Por fim, mesmo que os datagramas cheguem intactos, eles não chegam necessariamente na ordem em que foram enviados. Datagramas individuais podem seguir rotas diferentes da origem ao destino. Só porque o datagrama A é enviado antes do datagrama B não significa que o datagrama A chegará antes do datagrama B.

A camada de transporte é responsável por garantir que os pacotes sejam recebidos na ordem em que foram enviados e que nenhum dado seja perdido ou corrompido. Se um pacote for perdido, a camada de transporte pode pedir ao remetente para transmitir o pacote. Redes IP implementam isso adicionando um cabeçalho adicional a cada datagrama que contém mais informações. Existem dois protocolos principais neste nível. O primeiro é o Protocolo de Controle de Transmissão #TCP, é um protocolo de alta sobrecarga (*high-overhead*) que permite a retransmissão de dados perdidos ou corrompidos e a entrega de bytes na ordem em que foram enviados. O segundo protocolo, o Protocolo de Datagrama do Usuário (UDP), permite que o receptor detecte pacotes corrompidos, mas não garante que os pacotes sejam entregues na ordem correta (ou sequer que sejam entregues). No entanto, o UDP costuma ser muito mais rápido do que o TCP. O TCP é chamado de protocolo confiável; o UDP é um protocolo não confiável. 

## A Camada de Aplicação
A camada que entrega os dados ao usuário é chamada de camada de aplicação. As três camadas inferiores trabalham juntas para definir como os dados são transferidos de um computador para o outro. A camada de aplicação decide o que fazer com os dados depois que eles são transferidos. Por exemplo, um protocolo de aplicação como o HTTP (para a World Wide Web) garante que o seu navegador web exiba uma imagem gráfica como uma foto, e não como um longo fluxo de números. A camada de aplicação é onde a maior parte das partes de rede dos seus programaas passa o tempo.

Existe uma verdadeira sopa de letrinhas de protocolos da camada de aplicação: além do HTTP para a Web, existem SMTP, POP e IMAP para e-mail; FTP, FSP e TFTP para transferência de arquivos; NFS para acesso a arquivos; Gnutella e BitTorrent para compartilhamento de arquivos; o Protocolo de Iniciação de Sessão (SIP) e o Skype para comunicação de voz; e muitos, muitos mais. Além disso, seus programas podem definir seus próprios protocolos de camada de aplicação conforme necessário.

## IP, TCP e UDP
O IP, o protocolo de Internet, foi desenvolvido com patrocínio militar durante a Guerra Fria, e acabou com muitos recursos que interessavam aos militares. Primeiro, ele precisava ser robusto. A rede inteira não podia parar de funcionar se os soviéticos bombardeassem um roteador em Cleveland; todas as mensagens ainda precisavam chegar aos seus destinos pretendidos (exceto aquelas indo para Cleveland, é claro). Portanto, o IP foi projetado para permitir múltiplas rotas entre quaisquer dois pontos e para rotear pacotes de dados contornando roteadores danificados.

Segundo, os militares tinham muitos tipos diferentes de computadores, e todos eles precisavam ser capazes de conversar uns com os outros. Portanto, o IP precisava ser aberto e independente de plataforma; não bastava ter um protocolo para *mainframes* IBM e outro para PDP-11s. Os  *mainframes* IBM precisavam conversar com os PDP-11s e quaisquer outros computadores estranhos que  pudessem estar por aí.

Como existem múltiplas rotas entre dois pontos, e como o caminho mais rápido entre dois pontos pode mudar ao longo do tempo em função do tráfego de rede e outros fatores (como a existência de Cleveland), os pacotes que compõem um determinado fluxo de dados podem não seguir todas a a mesma rota. Além disso, eles podem não chegar na ordem em que foram enviados, se é que chegam. Para aprimorar o esquema básico, o TCP foi colocado sobre o IP para dar a cada extremidade de uma conexão a capacidade de confirmar o recebimento de pacotes IP e solicitar a retransmissão de pacotes perdidos ou corrompidos. Além disso, o TCP permite que os pacotes sejam remontados na extremidade receptora na mesma ordem em que foram enviados.

O TCP, no entanto, carrega uma quantidade considerável de sobrecarga (overhead). Portanto, se a ordem dos dados não for particularmente importante e se a perda de pacotes individuais não corromper completamente o fluxo de dados, os pacotes às vezes são enviados sem as garantias que o TCP fornece, usando o protocolo UDP. O UDP é um protocolo não confiável que não garante que os pacotes chegarão ao seu destino ou que chegarão na mesma ordem em que foram enviados. Embora isso fosse um problema para usos como transferência de arquivos, é perfeitamente aceitável para aplicativos em que a perda de alguns dados passaria despercebida pelo usuário final. Por exemplo, perder alguns _bits_ de um sinal de vídeo ou áudio não causará muita degradação; seria um problema maior se você tivesse que esperar que um protocolo como o TCP solicitasse a retransmissão dos dados ausentes. Além disso, códigos de correção de erros podem ser incorporados aos fluxos de dados UDP no nível da aplicação para compensar os dados ausentes.

Vários outros protocolos podem ser executados sobre o IP. O mais frequentemente solicitado é o ICMP, o Protocolo de Mensagens de Controle da Internet, que usa datagramas IP puros (_raw_) para retransmitir mensagens de erro entre _hosts_. O uso mais conhecido desse protocolo é no programa _ping_. O Java não oferece suporte ao ICMP, nem permite o envio de datagramas IP puros (em oposição a segmentos TCP ou datagramas UDP). Os únicos protocolos suportados pelo Java são o TCP e o UDP, e os protocolos da camada de aplicação construídos sobre eles. Todos os outros protocolos da camada de transporte, da camada de internet e de camadas inferiores, como ICMP, IGMP, ARP, RARP, RSVP e outros, só podem ser implementados em programas Java por meio da vinculação a código nativo (_native code_).

## Endereços IP e Nomes de Domínio
Como programador Java, não precisamos nos preocupar com o funcionamento interno do IP, mas precisamos conhecer sobre endereçamento. Cada computador em uma rede IPv4 é identificado por um número de quatro bytes. Normalmente, isso é escrito em um formato de quatro números separados por pontos *dotted quad format*, como 199.1.32.90, onde cada um dos quatro números é um byte sem sinal variando em valor de 0 a 255. Cada computador conectado a uma rede IPv4 possui um endereço exclusivo de quatro bytes. Quando os dados são transmitidos pela rede, o cabeçalho do pacote inclui o endereço da máquina para a qual o pacote se destina (o endereço de destino) e o endereço da máquina que enviou o pacote (o endereço de origem). Os roteadores ao longo do caminho escolhem a melhor rota para enviar o pacote inspecionando o endereço de destino. O <span style="background:#fff88f">endereço de origem</span> é incluído para que o destinatário saiba a quem responder.

Existem pouco mais de quatro bilhões de endereços IP possíveis, nem sequer um para cada pessoa no planeta, muito menos para cada computador. Para piorar a situação, os endereços não são alocados de forma muito eficiente. Em abril de 2011, a Ásia e a Austrália esgotaram seus estoques. Não havia mais endereços IPv4 disponíveis para serem alocados nessas regiões; e, desde então, eles tiveram que se virar reciclando e realocando de seu suprimento existente. Em setembro de 2012, a Europa também esgotou o seu. América do Norte, América Latina e África ainda têm alguns blocos de endereços IP sobrando para distribuir, mas eles não durarão muito mais tempo.

Uma lenta transição está em andamento para o IPv6, que usará endereços de 16 _bytes_. Isso fornece endereços IP suficientes para identificar cada pessoa, cada computador e, de fato, cada dispositivo no planeta. Os endereços IPv6 são habitualmente escritos em oito blocos de quatro dígitos hexadecimais separados por dois pontos, como FEDC:BA98:7654:3210:FEDC:BA98:7654:3210. Zeros à esquerda não precisam ser escritos. Um dois-pontos duplo (_double colon_), que pode aparecer no máximo uma vez em qualquer endereço, indica vários blocos de zeros. Por exemplo, FEDC:0000:0000:0000:00DC:0000:7076:0010 poderia ser escrito de forma mais compacta como FEDC::DC:0:7076:10. Em redes mistas de IPv6 e IPv4, os últimos quatro _bytes_ do endereço IPv6 às vezes são escritos como um endereço IPv4 com pontos. Por exemplo, FEDC:BA98:7654:3210:FEDC:BA98:7654:3210 poderia ser escrito como FEDC:BA98:7654:3210:FEDC:BA98:118.84.50.16.

Embora os computadores lidem muito bem com números, os seres humanos não são muito bons em lembrá-los. Portanto, o Sistema de Nomes de Domínio (DNS) foi desenvolvido para traduzir _hostnames_ (nomes de _host_) que humanos conseguem lembrar, como “[www.oreilly.com](https://www.oreilly.com)”, em endereços de Internet numéricos como 208.201.239.101. Quando programas Java acessam a rede, eles precisam processar tanto esses endereços numéricos quanto seus _hostnames_ correspondentes. Os métodos para fazer isso são fornecidos pela classe `java.net.InetAddress`, que é discutida no Capítulo 4.

Alguns computadores, especialmente servidores, têm endereços fixos. Outros, especialmente clientes em redes locais (_LANs_) e conexões sem fio, recebem um endereço diferente toda vez que são inicializados, frequentemente fornecido por um servidor DHCP. Em geral, você só precisa lembrar que os endereços IP podem mudar com o tempo e não deve escrever nenhum código que dependa de um sistema ter sempre o mesmo endereço IP. Por exemplo, não armazene o endereço IP local ao salvar o estado do aplicativo. Em vez disso, consulte-o novamente cada vez que o seu programa iniciar. Também é possível, embora menos provável, que um endereço IP mude enquanto o programa estiver em execução (por exemplo, se uma concessão DHCP expirar), então você pode querer verificar o endereço IP atual toda vez que precisar dele, em vez de armazená-lo em _cache_. Fora isso, a diferença entre um endereço atribuído dinâmica ou manualmente não é significativa para os programas Java.

Vários blocos e padrões de endereços são especiais. Todos os endereços IPv4 que começam com 10., de 172.16. até 172.31. e 192.168. não são roteáveis. Eles podem ser usados em redes internas, mas nenhum _host_ usando endereços nesses blocos tem permissão para acessar a Internet global. Esses endereços não roteáveis são úteis para construir redes privadas que não podem ser vistas na Internet. Os endereços IPv4 que começam com 127 (mais comumente 127.0.0.1) sempre significam o endereço de loopback local. Ou seja, esses endereços sempre apontam para o computador local, não importa em qual computador você o esteja executando. O _hostname_ para esse endereço costuma ser _localhost_. No IPv6, 0:0:0:0:0:0:0:1 (também conhecido como ::1) é o endereço de _loopback_. O endereço 0.0.0.0 sempre se refere ao _host_ de origem, mas só pode ser usado como endereço de origem, não de destino. Da mesma forma, presume-se que qualquer endereço IPv4 que comece com 0. (oito _bits_ zero) se refira a um _host_ na mesma rede local.

> Na versão 25 do Java, a classe #InetAddress continua sendo a pedra fundamental para representar endereços IP e resolver nomes de host (DNS). Ela não foi substituída nem descontinuada (deprecated).

O endereço IPv4 que usa o mesmo número para cada um dos quatro _bytes_ (ou seja, 255.255.255.255) é um endereço de _broadcast_ (transmissão). Os pacotes enviados para esse endereço são recebidos por todos os nós na rede local, embora não sejam roteados além da rede local. Isso é comumente usado para descoberta. Por exemplo, quando um cliente efêmero, como um _laptop_, é inicializado, ele envia uma mensagem específica para 255.255.255.255 para encontrar o servidor DHCP local. Todos os nós da rede recebem o pacote, mas apenas o servidor DHCP responde. Em particular, ele envia ao _laptop_ informações sobre a configuração da rede local, incluindo o endereço IP que o _laptop_ deve usar no restante de sua sessão e o endereço de um servidor DNS que ele pode usar para resolver _hostnames_.

## Ports
Endereços seriam tudo o que você precisaria se cada computador não fizesse mais do que uma coisa por vez. No entanto, os computadores modernos fazem muitas coisas diferentes ao mesmo tempo. O e-mail precisa ser separado das solicitações FTP, que precisam ser separadas do tráfego da web. Isso é realizado através de portas (_ports_). Cada computador com um endereço IP possui vários milhares de portas lógicas (65.535 por protocolo da camada de transporte, para ser exato). Estas são puramente abstrações na memória do computador e não representam nada físico, como uma porta USB. Cada porta é identificada por um número entre 1 e 65.535. Cada porta pode ser alocada para um serviço específico.

Por exemplo, o HTTP, o protocolo subjacente da Web, usa comumente a porta 80. Dizemos que um servidor web escuta (_listens_) na porta 80 por conexões de entrada. Quando os dados são enviados a um servidor web em uma máquina específica em um endereço IP específico, eles também são enviados a uma porta específica (geralmente a porta 80) nessa máquina. O receptor verifica a porta em cada pacote que recebe e envia os dados para qualquer programa que esteja escutando nessa porta. É assim que os diferentes tipos de tráfego são classificados.

Os números de porta entre 1 e 1023 são reservados para serviços bem conhecidos (_well-known services_) como _finger_, FTP, HTTP e IMAP. Em sistemas Unix, incluindo Linux e Mac OS X, apenas programas executados como _root_ (administrador) podem receber dados dessas portas, mas todos os programas podem enviar dados para elas. No Windows, qualquer programa pode usar essas portas sem privilégios especiais.

## Internet
A Internet é a maior rede baseada em IP do mundo. É um grupo amorfo de computadores em muitos países diferentes em todos os sete continentes (incluindo a Antártida) que se comunicam entre si usando protocolos IP. Cada computador na Internet possui pelo menos um endereço IP pelo qual pode ser identificado. Muitos deles também têm pelo menos um nome que mapeia para esse endereço IP. A Internet não pertence a ninguém, embora partes dela sim. Ela não é governada por ninguém, o que não quer dizer que alguns governos não tentem. É simplesmente uma coleção muito grande de computadores que concordaram em se comunicar de uma maneira padronizada.

A Internet não é a única rede baseada em IP, mas é a maior delas. Outras redes IP são chamadas de _internets_ com "i" minúsculo: por exemplo, uma rede interna de alta segurança que não está conectada à Internet global. _Intranet_ descreve de forma ampla as práticas corporativas de colocar muitos dados em servidores web internos que não são visíveis para usuários fora da rede local.

A menos que você esteja trabalhando em um ambiente de alta segurança que esteja fisicamente desconectado da rede mais ampla, é provável que a _internet_ que você usará seja a Internet. Para garantir que _hosts_ em redes diferentes na Internet possam se comunicar entre si, é necessário seguir algumas regras que não se aplicam a _internets_ puramente internas. As regras mais importantes lidam com a atribuição de endereços para diferentes organizações, empresas e indivíduos. Se todos escolhessem os endereços de Internet que quisessem aleatoriamente, conflitos surgiriam quase imediatamente quando computadores diferentes aparecessem na Internet com o mesmo endereço.

## Blocos de Endereços de Internet
Para evitar esse problema, blocos de endereço IPv4 são atribuídos aos provedores de serviços de Internet (ISPs) por seu registro regional de Internet. Quando uma empresa ou organização deseja configurar uma rede baseada em IP conectada à Internet, seu ISP atribui a eles um bloco de endereços. Cada bloco tem um prefixo fixo. Por exemplo, se o prefixo for 216.254.85, a rede local poderá usar endereços de 216.254.85.0 a 216.254.85.255. Como este bloco fixa os primeiros 24 _bits_, ele é chamado de /24. Um /23 especifica os primeiros 23 _bits_, deixando 9 _bits_ para 2^9 ou 512 endereços IP locais no total. Uma sub-rede /30 (a menor possível) especifica os primeiros 30 _bits_ dos endereços IP dentro da sub-rede, deixando 2 _bits_ para 2^2 ou 4 endereços IP locais no total. No entanto, o endereço mais baixo em um bloco é usado para identificar a própria rede, e o maior endereço em um bloco é um endereço de _broadcast_ para a rede, então você tem dois endereços disponíveis a menos do que poderia esperar inicialmente.

### Tradução de Endereços de Rede (NAT)
Devido à crescente escassez e à demanda por endereços IP puros, a maioria das redes hoje usa a Tradução de Endereços de Rede (NAT - _Network Address Translation_). Em redes baseadas em NAT, a maioria dos nós possui apenas endereços locais e não roteáveis, selecionados entre 10.x.x.x, 172.16.x.x a 172.31.x.x, ou 192.168.x.x. Os roteadores que conectam as redes locais ao ISP traduzem esses endereços locais para um conjunto muito menor de endereços roteáveis.

Por exemplo, a cerca de uma dúzia de nós IP no meu apartamento compartilham um único endereço IP visível externamente. O computador no qual estou digitando isso tem o endereço IP 192.168.1.5, mas na sua rede esse endereço pode se referir a um _host_ completamente diferente, se é que existe. Você também não conseguiria acessar meu computador enviando dados para 192.168.1.5. Em vez disso, você teria que enviar para 216.254.85.72 (e mesmo assim, os dados só passariam se eu tivesse configurado meu roteador NAT para repassar as conexões de entrada para 192.168.1.5).

O roteador monitora minhas conexões de saída e de entrada e ajusta os endereços nos pacotes IP. Para um pacote de saída, ele altera o endereço de origem para o endereço externo do roteador (216.254.85.72 na minha rede). Para um pacote de entrada, ele altera o endereço de destino para um dos endereços locais, como 192.168.1.12. Como exatamente ele rastreia quais conexões vêm e para quais computadores internos são direcionadas não é particularmente importante para um programador Java. Desde que suas máquinas estejam configuradas corretamente, esse processo é quase totalmente transparente. Você só precisa lembrar que os endereços externos e internos podem não ser os mesmos.

Eventualmente, o IPv6 deverá tornar a maior parte disso obsoleta. O NAT não terá sentido, embora os _firewalls_ ainda sejam úteis. As sub-redes ainda existirão para roteamento, mas serão muito maiores.

> O funcionamento do NAT continua **exato e indispensável** hoje. Contudo, a previsão de que o IPv6 tornaria o NAT "obsoleto" está **defasada**: a transição é lenta, o IPv4 segue vivo através do CGNAT, e o NAT virou um padrão informal de segurança.

## Firewalls
Existem algumas pessoas mal-intencionadas na Internet. Para mantê-las fora, geralmente é útil configurar um único ponto de acesso para uma rede local e verificar todo o tráfego que entra ou sair desse ponto de acesso. O hardware e o software que ficam entre a Internet e a rede local, verificando todos os dados que entram ou saem para garantir que sejam legítimos (kosher), são chamados de #firewall.

O firewall geralmente faz parte do roteador que conecta a rede local à internet mais ampla e pode realizar outras tarefas, com a tradução de endereços de rede NAT. Por outro lado, o _firewall_ pode ser uma máquina separada. Sistemas operacionais modernos, como o Mac OS X e o Red Hat Linux, geralmente possuem _firewalls_ pessoais integrados que monitoram apenas o tráfego enviado para aquela máquina específica. De qualquer forma, o _firewall_ é responsável por inspecionar cada pacote que passa por sua interface de rede e aceitá-lo ou rejeitá-lo de acordo com um conjunto de regras.

A filtragem geralmente é baseada em endereços de rede e portas. Por exemplo, todo o tráfego vindo da rede Classe C `193.28.25.x` pode ser rejeitado porque você teve experiências ruins com _hackers_ dessa rede no passado. Conexões SSH de saída podem ser permitidas, mas conexões SSH de entrada podem não ser. Conexões de entrada na porta 80 (web) podem ser permitidas, mas apenas para o servidor web corporativo. _Firewalls_ mais inteligentes examinam o conteúdo dos pacotes para determinar se devem aceitá-los ou rejeitá-los. A configuração exata de um _firewall_ — quais pacotes de dados têm permissão para passar e quais não têm — depende das necessidades de segurança de cada site. O Java não tem muito a ver com _firewalls_ — exceto na medida em que eles frequentemente ficam no seu caminho.

- **Fundamento Atual:** O conceito de filtragem por pacotes (IP de origem/destino, porta e direção) continua sendo a base de qualquer firewall de rede ou pessoal (como o `iptables`/`nftables` no Linux ou o Windows Defender Firewall).

- **Evolução Tecnológica:** O texto menciona que "_firewalls mais inteligentes olham o conteúdo_". Hoje, isso evoluiu para os chamados **NGFW (Next-Generation Firewalls)** e firewalls de camada de aplicação (**WAF - Web Application Firewall**), que analisam profundamente o tráfego HTTP/HTTPS para bloquear ataques modernos (como injeções de código SQL ou cross-site scripting), indo muito além do bloqueio simples de portas e IPs. #WAF

- **Exemplos Históricos:** As menções ao "Mac OS X" e "Red Hat Linux" como referências de modernidade entregam a idade do texto original, embora a lógica interna permaneça idêntica nos sistemas atuais.

## Proxy Servers
Servidores proxy estão relacionados aos #firewalls. Se um #firewall impede que os hosts de uma rede façam conexões diretas com o mundo externo, um servidor proxy pode atuar como um intermediário. Assim, uma máquina que é impedida de se conectar à rede externa por um firewall faria uma solicitação de uma página da web a partir do servidor proxy local em vez de solicita-la diretamente do servidor web remoto. O servidor proxy então solicita a página ao servidor web e encaminharia a resposta de volta ao solicitante original. Proxies também podem ser usados para serviços FTP e outras conexões. Uma das vantagens de segurança de usar um servidor proxy é que os _hosts_ externos só ficam sabendo sobre o servidor proxy. Eles não descobrem os nomes e endereços IP das máquinas internas, tornando mais difícil invadir sistemas internos.

Enquanto os _firewalls_ geralmente operam no nível da camada de transporte ou de internet, os servidores proxy normalmente operam na camada de aplicação. Um servidor proxy tem um entendimento detalhado de alguns protocolos de nível de aplicação, como HTTP e FTP. (A exceção notável são os servidores proxy SOCKS que operam na camada de transporte e podem atuar como proxy para todas as conexões TCP e UDP, independentemente do protocolo da camada de aplicação). Os pacotes que passam pelo servidor proxy podem ser examinados para garantir que contenham dados apropriados para seu tipo. Servidores proxy também podem ser usados para implementar *cache* local. Quando um arquivo é solicitado a um servidor web, o servidor proxy primeiro verifica se o arquivo está em seu #cache. Se o arquivo estiver no cache, o proxy serve o arquivo a partir do cache em vez da internet. Se o arquivo não estiver no _cache_, o servidor proxy recupera o arquivo, o encaminha ao solicitante e o armazena no _cache_ para a próxima vez que for solicitado. Esse esquema pode reduzir significativamente a carga em uma conexão de Internet e melhorar muito o tempo de resposta. A America Online administra uma das maiores fazendas (_farms_) de servidores proxy do mundo para acelerar a transferência de dados para seus usuários. Se você observar o arquivo de _log_ de um servidor web, provavelmente encontrará alguns acessos de clientes no domínio aol.com, mas não tantos quanto esperaria, considerando os mais de três milhões de assinantes da AOL. Isso ocorre porque os servidores proxy da AOL fornecem muitas páginas a partir de seu _cache_ em vez de solicitá-las repetidamente uns para os outros. Muitos outros grandes ISPs fazem o mesmo.

O maior problema com servidores proxy é a incapacidade deles de lidar com quase todos os protocolos. Geralmente, protocolos estabelecidos como HTTP, FTP e SMTP têm permissão para passar, enquanto protocolos mais recentes como BitTorrent não têm. (Alguns administradores de rede consideram isso uma vantagem). No mundo em rápida mudança da Internet, isso é uma desvantagem significativa. É uma desvantagem particular para programadores Java porque limita a eficácia de protocolos customizados. Em Java, é fácil e frequentemente útil criar um novo protocolo que seja otimizado para a sua aplicação. No entanto, nenhum servidor proxy jamais entenderá esses protocolos únicos. Consequentemente, alguns desenvolvedores começaram a tunelar seus protocolos através do HTTP, mais notavelmente com o SOAP. No entanto, isso tem um impacto negativo significativo na segurança. O _firewall_ normalmente está lá por um motivo, não apenas para irritar os programadores Java.

## The Client/Server Model
A maior parte da programação de rede moderna é baseada em um modelo cliente/servidor. Um aplicativo cliente/servidor normalmente armazena grandes quantidades de dados em um servidor caro e de alta potência, ou em uma nuvem de servidores, enquanto a maior parte da lógica do programa e a interface do usuário são tratadas pelo software cliente em execução em computadores pessoais relativamente baratos. Na maioria dos casos, um servidor atua principalmente enviando dados, enquanto um cliente atua principalmente recebendo-os; mas é raro que um programa envie ou receba exclusivamente. Uma distinção mais confiável é que um cliente inicia uma conversa enquanto um servidor espera que os clientes iniciem conversas com ele. A Figura 1-5 ilustra ambas as possibilidades. Em alguns casos, o mesmo programa pode ser tanto um cliente quanto um servidor.

Você já está familiarizado com muitos exemplos de sistemas cliente/servidor. Em 2013, o sistema cliente/servidor mais popular na Internet era a Web. Servidores web como o Apache respondem a solicitações de clientes web como o Firefox. Os dados são armazenados no servidor web e enviados aos clientes que os solicitam. Tirando a solicitação inicial por uma página, quase todos os dados são transferidos do servidor para o cliente, e não do cliente para o servidor. O FTP é um serviço mais antigo que se encaixa no modelo cliente/servidor. O FTP usa protocolos de aplicação e softwares diferentes, mas ainda é dividido em servidores FTP que enviam arquivos e clientes FTP que recebem arquivos. As pessoas frequentemente usam o FTP para fazer _upload_ de arquivos do cliente para o servidor, então é mais difícil dizer que a transferência de dados ocorre primariamente em uma única direção, mas ainda é verdade que um cliente FTP inicia a conexão e o servidor FTP responde.

Nem todas as aplicações se encaixam facilmente em um modelo cliente/servidor. Por exemplo, em jogos em rede, parece provável que ambos os jogadores enviem e recebam dados quase igualmente (pelo menos em um jogo justo). Esses tipos de conexões são chamados de _peer-to-peer_ (ponto a ponto). O sistema telefônico é o exemplo clássico de uma rede _peer-to-peer_. Cada telefone pode ligar para outro telefone ou receber ligações de outro telefone. Você não precisa comprar um telefone para fazer chamadas e outro para recebê-las.

O Java não possui comunicação *peer-to-peer* explícita em sua API de rede principal. No entanto, os aplicativos podem facilmente oferecer comunicação peer-topeer de várias maneiras, mais comumente atuando tanto como servidor quanto como cliente. Alternativamente, os pontos #peers podem se comunicar uns com os outros por meio de um programa servidor intermediário que encaminha dados de um ponto para os outros pontos. Isso resolve de forma elegante o problema e descoberta de como dois pontos se encontram.

## Internet Standards
Este livro discute vários protocolos de Internet da camada de aplicação, mais notavelmente o HTTP. No entanto, este não é um livro sobre esses protocolos. Se você precisar de informações detalhadas sobre qualquer protocolo, a fonte definitiva é o documento de padrões do protocolo.

Embora existam muitas organizações de padronização no mundo, as duas que produzem a maioria dos padrões relevantes para programação de redes e protocolos da camada de aplicação são a _Internet Engineering Task Force_ (IETF) e o _World Wide Web Consortium_ (W3C). A IETF é um órgão relativamente informal e democrático, aberto à participação de qualquer parte interessada. Seus padrões são baseados em "consenso aproximado e código em execução" e tendem a seguir, em vez de liderar, as implementações. Os padrões da IETF incluem TCP/IP, MIME e SMTP. O W3C, por outro lado, é uma organização de fornecedores, controlada por corporações-membros pagantes, que exclui explicitamente a participação de indivíduos. Em grande parte, o W3C tenta definir padrões antes da implementação. Os padrões do W3C incluem HTTP, HTML e XML.
